# 小说工坊 AI · 长期目标与 Harness 优化纲要

> **文档性质**：长期目标描述（不是排期表，不是需求文档）
> **生效版本**：v1.0 · 2026-11-11 · 基线 v4.83.0
> **维护方式**：每个阶段收口时更新「§二 基线」与「§十 变更记录」；目标本身不轻易改
> **配套**：`docs/PLAN.md`（战术排期）、`docs/progress/program-status.json`（质量台账）、`docs/handbook/`（操作手册）

---

## 〇、一句话目标

> **让「小说工坊 AI」成为一个可以长期自持演化的 AI 写作工作台：
> 作者用自然语言表达意图，插件自主完成从设定考据、结构设计、正文生成到质量结算的全链路，
> 并且每一步都「可解释、可验证、可回退」。**

其中**可验证**是长期主线。理由见 §四。

---

## 一、三层目标

| 层 | 目标 | 判断标准 |
|---|---|---|
| **产品层** | 作者不需要理解插件内部结构，就能拿到可发布的稿子 | 新用户 30 分钟内跑通「建项目 → 拆解参考书 → 写一章 → 结算」 |
| **Harness 层** | 插件的 agent 执行层能自主规划、调用工具、管理上下文、从失败中恢复 | agent 在无人干预下完成一个完整创作阶段，失败时能自我诊断 |
| **工程层** | 代码库在 40 万行量级上仍能高速安全演进 | 新增功能不增加「静默失效」；28 步门禁始终绿灯；bundle 不失控 |

三层的关系：**产品层是目的，Harness 层是手段，工程层是刹车**。工程层永远不能让前两层停下来，但可以让它们不翻车。

## 三、Harness 全景（本插件的执行层）

### 3.1 三个同心圆

```
┌─────────────────────────────────────────────────────────┐
│  编排层  engine/agent/harness/                          │
│  harness-engine(575) · agent-loop(586) ·                │
│  tool-registry(275) · creation-plan(66)                 │
├─────────────────────────────────────────────────────────┤
│  能力层  host-tools(976) + tool-catalog + command-registry│
│  文件读写 · 命令执行 · 知识检索 · 实体生成 · 结算        │
├─────────────────────────────────────────────────────────┤
│  上下文层  prompt-sections(141) · context-fit(124)      │
│  spill-store(106) · tool-result-pruner(59)              │
│  session-log(246) · session-snapshot(236)               │
└─────────────────────────────────────────────────────────┘
```

### 3.2 关键事实

- **Harness 层只有约 4,000 行**，却决定了整个插件的智能程度上限。
- `host-tools.ts`（976 行）是**权限边界**所在：16 条权限测试守着命令白名单、模式守卫、路径穿越、参数夹紧。
- `engine/agent/dsh/`（约 900 行）是外部 harness 桥接（`dsh-session` / `dsh-process` / `dsh-protocol` / `dsh-launch`），有独立的隔离门禁 `check:dsh-isolation`。
- **上下文层是当前最薄弱的一环**：`context-fit` 只有 124 行，却要负责在 8K 本地窗口下决定"什么进 prompt"。

### 3.3 三条数据流（长期都要守住的链路）

```
① 知识流  拆解书籍 → 向量库 → 检索 → 注入 prompt → 正文 → rag_sources 归因
② 风格流  参考书/知识库 → 指纹(三层) → 强度(两层) → 注入 → 正文
③ 约束流  官方考据 → 同人设定(审核) → 绑定项目 → 注入 → 正文
```

**三条流的共同弱点**：任何一环断掉，下游都会**静默退化为"没有约束地写"**，用户看不出区别。这是 §四 的核心命题。

## 四、核心命题（为什么是"可验证"）

### 4.1 从实战中提炼

2026-11-11 一轮审计修掉 5 个缺陷，**全部是静默失效**：

| # | 缺陷 | 用户感知 |
|---|---|---|
| 1 | 拆解向量被两道关卡挡在 RAG 外 | 拆解了书，写作时完全没用上，**无报错** |
| 2 | `samples` 为空却标记 `vectorStatus='done'` | 界面显示"向量化成功"，实际空库 |
| 3 | 嵌入不可用时检索整体抛错 | 知识库完全不可用，只有控制台有日志 |
| 4 | 指纹消费链路 5/6 路径首次运行恒空 | 风格约束消失，**无报错** |
| 5 | 向导保存绕过同人设定审核闸门 | 未核实设定被当作原作约束 |

**共性**：代码"成功执行"了，但**用户以为生效的东西没有生效**。

### 4.2 命题

> **每一条"用户以为生效了"的链路，都必须真的生效，并且能被证明生效。**

"被证明"有三个层次：
1. **代码层**：有端到端测试覆盖"写进去 → 读出来"（不只是单元测试各自的 mock）
2. **运行层**：降级/失败必须产生**用户可见**的信号，不能只写日志
3. **界面层**：UI 上能看到"当前这条链路是通的还是断的、断在哪"

### 4.3 为什么这是长期任务

- 功能会持续增加，每条新功能都会带来新的"链路"，**验证机制必须跟着长**，否则欠账越滚越大
- 静默失效无法一次性清零：它是设计模式的产物（"读共享内存 + 调用方负责刷新"），只能靠**机制**持续压制
- 这条主线不会"做完"，只会"维持"——适合作为长期目标

## 五、优化主战场（按价值排序）

### P0 · 链路自证（可验证的核心）

| 目标 | 验收标准 |
|---|---|
| 三条数据流各有端到端断言 | 每条流至少 1 个"写→读→生效"的集成测试，不 mock 中间层 |
| 生效状态 UI 可见 | 知识库/指纹/同人设定三个界面都能看到"当前生效 N 条 / 断在哪一环" |
| 降级必可见 | 任何 fallback 都产生 Notice 或横幅（已有 `check:silent-failures` 守代码层） |

### P1 · 静默失效归零

| 目标 | 验收标准 |
|---|---|
| "读共享状态"必须有自愈或显式契约 | 禁止"依赖调用方记得刷新"的设计（本次指纹教训） |
| 状态标记必须与真实数据一致 | 不允许"标记成功但实际为空"（本次向量化教训） |
| 审核闸门不可绕过 | 所有写入正式目录的路径都过闸门（本次向导教训） |

### P2 · 可用性（发现与引导）

| 目标 | 验收标准 |
|---|---|
| 依赖缺失可自诊断 | 嵌入模型/Ollama/API Key 缺失时，界面直接给"缺什么 + 去哪里配" |
| 修复入口就近 | 失败项旁边就有重试入口，不需要去设置页全局重算 |
| 新用户引导 | 空态带下一步动作，不是空白面板 |

### P3 · Harness 自主性

| 目标 | 验收标准 |
|---|---|
| Agent 能诊断常见断链 | agent 收到"为什么没生效"的问题时，能查向量库/指纹/设定状态并给出结论 |
| 上下文预算可控 | 8K 窗口下不因注入膨胀而截断关键内容 |
| 工具权限边界不退化 | `host-tools` 16 条边界测试始终绿 |

### P4 · 可测性与体积

| 目标 | 验收标准 |
|---|---|
| `ui/` 覆盖率从 8.68% 提升 | 每阶段至少 +5pp，靠"抽纯逻辑模块"而非 DOM 测试 |
| 零覆盖大文件逐步消化 | `check:view-tests` 基线只降不升，每阶段至少 −10 个 |
| bundle 不失控 | 每阶段净增 ≤ 50 KB，且每次上调基线必须写清归因 |

## 六、分阶段路线

> 每阶段 4–8 轮（一轮 = 一次完整提交 + 门禁绿灯 + 台账记录）。阶段之间可并行，但**A 必须先于 B**。

### 阶段 A｜链路自证（当前阶段）

**目标**：三条数据流各有一条"写→读→生效"的集成测试 + 界面上能看到生效状态。

| 交付物 | 验收 |
|---|---|
| A1 知识流端到端测试 ✅ | `tests/integration/knowledge-flow-e2e.test.ts`（5 条，真实向量库/检索/注入/归因） |
| A2 风格流端到端测试 ✅ | `tests/integration/style-flow-e2e.test.ts`（7 条，真实三层指纹库 + 向量库 + PromptBuilder） |
| A3 约束流端到端测试 ✅ | `tests/integration/constraint-flow-e2e.test.ts`（6 条，真实 Vault + 绑定 + 解析 + 注入） |
| A4 生效状态面板 ✅ | `ui/views/link-status.ts`：三链路环节级通/断判定 + 断点定位，已接入知识库/指纹库/同人设定三界面（复用现有 CSS 零新增样式） |

**退出条件**：三条流各有集成测试且能在 CI 跑 ✅；界面能看到链路状态 ✅ —— **阶段 A 已收口**。

### 阶段 B｜静默归零

**目标**：消除"设计性静默"——所有降级、跳过、回退都有可见出口。

| 交付物 | 验收 |
|---|---|
| B1 降级事件统一出口 ✅ | 可统计（`summarizeDegradations`/`getSummary`）+ 三界面链路状态展示运行时降级 |
| B2 状态标记一致性审计 | 每个 `*Status` 字段都有"标记与真实数据一致"的测试 |
| B3 刷新契约收口 | 所有"读共享内存"的 getter 要么自愈，要么有显式 `reload` 前置断言 |
| B4 闸门审计 ✅ | 4 条写正式目录路径全部有闸门并固化为契约（`fanfic-gate-audit` 7 条，含防回归断言） |

**退出条件**：`check:silent-failures` 覆盖到"设计性静默" ✅；零已知静默失效 ✅ —— **阶段 B 已收口**。

### 阶段 C｜Harness 自主

**目标**：agent 能回答"为什么没生效"并给出修复建议。

| 交付物 | 验收 |
|---|---|
| C1 诊断工具集 ✅ | `diagnose_flow` 工具（knowledge/style/constraint/all），判定复用 `shared/link-status-compute`——agent 与界面断点必然一致；13 条测试 |
| C2 上下文预算策略 ✅ | 8K 窗口量化基准：可用输入 3692 token ≈ 5538 字符；工具结果裁剪落点、overBudget 显式失败、最后一条指令必保留；17 条基准测试 |
| C3 失败自恢复 ✅ | 向量库三类损坏场景矩阵（跳过单文件/全损坏保留内存可重试/不删用户文件）；5 条测试 + 其余降级路径对照表 |

**退出条件**：给定"我的设定为什么没进正文"，agent 能自主定位到具体环节 ✅ —— **阶段 C 已收口**。

### 阶段 D｜规模与可维护

**目标**：40 万行量级下，新功能不拖慢演进。

| 交付物 | 验收 |
|---|---|
| D1 零覆盖大文件消化 | 94 → ≤40 |
| D2 `ui/` 覆盖率 | 8.68% → ≥30%（`ui/views` 域） |
| D3 模块边界巩固 | `check:deps` 零违规，services 不依赖 engine |
| D4 文档与手册同步 | `check:docs` 覆盖所有活跃文档 |

**D1 执行说明（2026-11-11 调研修正）**：

清点 94 个零覆盖文件后有一个结构性发现——**它们绝大多数已是纯 DOM 渲染壳**。
前几轮已把可抽逻辑抽走（`kb-panels-logic` / `kb-card-logic` / `kb-format` /
`kb-book-filter` / `kb-task-panel` / `book-detail-metrics` 等 6+ 个纯模块），
剩下的是 `renderXxxTab` / `showXxxModal` 这类方法。

因此 D1 **不采用「硬压数字」的推进方式**（例如给主文件加 `import type` 骗过门禁），
而是坚持红线「不追求 ui 总体覆盖率数字」：

1. 每轮只在**确实还有逻辑**的文件上抽 1 个纯模块 + 写真实测试
2. 数字随真实可测性提升而自然下降，不为达标而制造空测试
3. 若某个文件确认「只剩渲染、无逻辑可抽」，在台账里标注并说明理由，
   而不是假装它被覆盖了

这条说明本身是 D 阶段的一部分：**承认约束比伪造进度更有价值**。

**D2 量化证据（2026-11-11 实测 `npm run test:cov`）**：

`ui/views` 域整体 8.68%，但内部分化极端——

| 类别 | 代表文件 | lines 覆盖 |
|---|---|---|
| **抽出的纯模块** | `kb-card-logic` / `kb-task-panel` / `kb-book-filter` / `fingerprint-view-logic` | **100%** |
| 同上（次优） | `book-detail-metrics` / `kb-format` / `kb-panels-logic` | 95–98.5% |
| **视图壳** | `book-detail-renderer` / `knowledge-base-view` / `writing-fingerprint-view` | **0.1–0.42%** |
| 同上 | `knowledge-base-modals` / `kb-config-panel` | 0–0.17% |

结论：**ui 覆盖率被巨型视图壳拖累，不是"没测试"，而是"逻辑还在壳里"**。
提升路径只有一条——继续抽纯模块（每抽一个，该部分从 0.x% 跳到 ~100%），
写 DOM 测试对本项目无性价比（与 ADR `g7-4-dom-testing-decision.md` 一致）。

**退出条件**：新人能在 1 天内理解三条数据流并提交一个有测试的改动。

## 七、红线（长期不做）

| 红线 | 理由 |
|---|---|
| **不重切 `co-writing-view.ts`** | 已实证：三次切片累计 +3,664B，适配层占净增 100% |
| **不追求 `ui/` 总体覆盖率数字** | DOM 测试成本远高于收益；靠抽纯逻辑模块提升，不为数字写测试 |
| **不为过门禁悄悄上调基线** | 每次上调必须 `--note` 写清归因；基线是刹车不是装饰 |
| **不用模型记忆代替官方来源** | 同人设定只能依据官方/原著，衍生作品永不作为设定来源 |
| **不自动放行审核** | 联网验证结论只写 meta，人工审核是唯一放行口 |
| **不破坏数据可回退性** | 任何写操作都要么幂等、要么有 journal/备份 |
| **不在未确认时打 tag / 发 Release** | 发版需用户明确确认 |

## 八、衡量体系

### 8.1 主指标（每阶段收口时记录）

| 指标 | 当前 | 目标 |
|---|---|---|
| 已知静默失效数 | 0（本轮清零） | 恒为 0 |
| 三条数据流端到端测试 | **3 条链路 / 18 个用例** ✅ | 3 条 |
| `ui/` 覆盖率 | 8.68% | ≥30%（阶段 D） |
| 零覆盖 >200 行文件 | 94 | ≤40（阶段 D） |
| `main.js` 体积 | 4,897,792 B | ≤5 MB 且阶段净增 ≤50 KB |
| 门禁绿灯率 | 100% | 100% |

### 8.2 反自欺规则

1. **数字必须可复现**：每个数字后面要能指出生成它的命令
2. **测试要断言意图，不是断言实现**：`dimensions` 断言"含目标维度且不含其他拆解维度"，不是断言精确数组
3. **基线只降不升**：上升必须写归因，且归因要能被第二个人复核
4. **降级要可观测**：任何 `catch` 里的"静默返回"都必须有用户可见出口或显式注释说明为何不需要
5. **不把"代码执行成功"当成"功能生效"**：这是本项目的头号教训

### 8.3 每轮必做

```powershell
cd .obsidian/plugins/novel-writer-ai
npm run preflight          # 28 步门禁，必须 EXIT=0
node scripts/record-iteration.mjs --type <type> --deliverable "..." --gates "..."
git push origin master     # 已放行；tag/Release 需用户确认
```

## 九、风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 功能持续增加导致验证欠账扩大 | 静默失效回流 | 阶段 A 的"链路自证"必须先于新功能 |
| 覆盖率提升挤压功能开发 | 进度变慢 | 只对"核心链路"要求覆盖，不追求全局数字 |
| bundle 逼近 5 MB | 无法加功能 | 每阶段净增预算 ≤50 KB；优先用工具类不新增 CSS |
