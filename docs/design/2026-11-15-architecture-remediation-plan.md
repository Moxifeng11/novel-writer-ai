# 架构整改计划（C → B → A）：从「能写」到「写得好」

> 目标文档。回答一个问题：**为什么插件总是解决不了架构问题、写书效果不理想**，以及**按什么顺序、改哪些地方才能真正改善**。
> 前置材料：`docs/audit/2026-11-15-plugin-data-model-audit.md`、`docs/audit/2026-11-15-atomization-audit.md`、`docs/design/2026-11-15-v4-status.md`。
> 原则：先量基线、再动结构；每步默认关闭、可回退；**没有指标改善的改动视为未完成**。

## 一、问题定位（为什么效果不理想）

三层缺陷，按影响排序：

| 层 | 缺陷 | 后果 | 现状 |
|---|---|---|---|
| 数据层 | 同一事实多份真源（章节状态 4 份、事实 5 处、伏笔 2 套、关系 4 通道）；短篇/剧本旁路 BodyWriter | 脏数据回流，下一章基于错误事实继续写 | M13/M14 只收口了台账与设定 |
| 校验层 | 一致性/OOC/节奏只出报告，不回注、不强制修订 | 错误一次成型，逐章累积（人设漂移、设定冲突） | M6/M10/M11 做了「前馈注入」，未做「后验闭环」 |
| 生成层 | 静态选片装配：一次决定注入什么，模型无法生成中按需取 | 需要的信息没进来、不需要的占满窗口 → 截断/重试/漏信息 | M4/M5 做了场景级检索与 `request_context` 工具，但**未进入生成循环** |

一句话：**喂给模型的信息结构不对、不够、错了没人纠**。

## 二、设计原则（后续所有改动必须满足）

1. **单一真源**：一个事实只有一处权威写入点；其余为派生视图或缓存。
2. **单一写入管道**：所有正文/单元写入走 BodyWriter + FileTx（版本、锁、格式契约、不变量一致）。
3. **结构化约束优先于长文本**：能写成「ID + 一句话约束」的，不要塞整份 md。
4. **闭环**：生成 → 校验 → 定向修订 → 再校验；不允许「生成即结束」。
5. **可测可退**：每个行为开关默认关；有指标对比；有回退路径。

## 三、指标体系（先量基线，再谈改善）

### 3.1 代理指标（自动采集，现有埋点）

| 指标 | 来源 | 目标 |
|---|---|---|
| 截断次数 | `step-runner` `warnIfTruncated` / `injection-ledger` | → 0 |
| 重试率 | `step-runner-retry` | 下降 |
| 单章注入 token | `injection-ledger` | 下降 ≥40% |
| 在场事实覆盖率 | M5 覆盖报告（`coverage.missing`） | 100% |
| 一致性矛盾数/章 | `矛盾.json` + CED | 不增加高危 |
| OOC 高危数/章 | 人物一致性报告 | 下降 |
| 质检通过率 | `quality-history` | 上升 |
| 生成后回写失败数 | `回写审查.json` | → 0 |
| 修订次数/章 | `autoRevisionAfterQC` 记录 | 先记录再优化 |

### 3.2 主观指标（必须，否则代理指标可能"优化"坏质量）

- 每阶段结束抽 3 章人工评分（1–5）：人设一致 / 情节连贯 / 节奏 / 文风。
- 评分需在**改动前后同章同模型**对比。

### 3.3 基线采集（C 阶段第 0 步）

在真实项目上跑 1 章，导出：`injection-ledger` 注入溯源、`usage-ledger` token、质检结果、矛盾数、人工评分。**没有基线不动结构**。

## 四、阶段 C：单一写入管道（代价低，先做）

### C1 收口旁路写入（短篇/剧本）

- 现状：`engine/mode-unit-writer.ts` 自行 `vault.modify` + 手拼 frontmatter，绕过 `BodyWriter`（无版本备份/无格式契约/无写锁/无广播）。
- 改法：单元落盘改走 `BodyWriter`（新增 `unit` 写入类型），复用：覆盖前 saveVersion、`normalizeBodyText` 格式契约、`applyInvariants`（status 不降级）、写锁、`body-written` 广播。
- 验收：单元重生成会留版本；frontmatter 不变量与长篇一致；`mode-unit-writer` 相关测试全绿。

### C2 章节状态单一真源

- 现状：正文 frontmatter `status` / 结算表「结算状态」/ 章节状态快照 / UI 现算，四处口径。
- 改法：正文 frontmatter 为唯一权威；结算表与快照降级为派生（写入时从正文派生，读取时以正文为准）；`shared/chapter-progress` 只读正文。
- 验收：对同一章，四处读取结果一致（加一致性测试）。

### C3 事实/一致性产物收口

- 现状：`事实库.json` / `断言.json` / `剧情记忆/*_摘要.md` / `事实索引.json` 四结构。
- 改法：以 `断言.json`（结构化、带 ID/来源/严重度）为权威；事实库与摘要改为派生；`事实索引` 删除或改为索引缓存。
- 验收：一致性审核、写作前馈、质量面板读同一份；写入只有一个入口（`assertion-store`）。

### C4 关系四通道收口

- 现状：frontmatter wiki-link / `关系状态.md` 数值表 / `设定图/关系.json` / 章节 `涉及*` 数组。
- 改法：`关系状态.md` 为权威（已派生视图化），`设定图/关系.json` 降为缓存，frontmatter 只保留「主要关系」展示用途，章节 `涉及*` 改为 ID 数组（写入时由结算生成）。
- 验收：改一处关系，实体图/面板/注入三者一致。

### C5 写入失败可回滚

- 改法：所有多文件写入走 `FileTxService`（事务 + journal）；结算已有，补齐模式单元与迁移路径。
- 验收：模拟第 2 个文件写失败，第 1 个已回滚。

**C 阶段出口**：脏数据来源归零；后续 A/B 在干净数据上运行。

## 五、阶段 B：校验闭环（收益大）

### B1 生成后自动校验

- 正文步完成后自动触发（可配置）：一致性断言核对（按本章在场 ID）+ 人物一致性 + 节奏偏离 + 质量门禁。
- 复用现有：`character-consistency-checker`、`quality-gate`、`assertion` 模型、`rhythm-baseline-model`。
- 输出统一「校验报告」（结构化），供 B2 消费。

### B2 定向修订（核心）

- 现状：`autoRevisionAfterQC` 只按质量问题清单改，且不覆盖一致性/OOC/节奏。
- 改法：把 B1 报告转为**定向修订指令**（问题类型 + 定位 + 约束），复用现有修订通道；只改问题段落，不整章重写。
- 硬约束：修订后必须重跑 B1；仍不通过则标记「待人工」，不静默通过。

### B3 校验前馈升级

- 现状：把断言/节奏/口吻作为「一段文本」塞进 prompt。
- 改法：改为**结构化约束块**（`ID + 约束 + 来源`，按在场 ID 精确匹配，分批），并记录「本次注入的约束 ID」到注入账本，便于归因。

### B4 质量面板闭环

- 质量面板展示：每章校验通过率、问题类型分布、修订次数、矛盾趋势。
- 作用：让你能看见「写崩在哪一章、为什么」。

**B 阶段出口**：错误不再累积；同一章可自动修订到通过（或明确标记待人工）。

## 六、阶段 A：生成循环化（收益最大，风险最高）

### A1 正文步改为场景级循环

- 现状：一次拼 prompt → 一次调用。
- 改法：`step-runner` 正文步改为场景循环：每场 = 「装配 → 生成 → 校验 → 不够则 `request_context` 补 → 再生成」。
- 复用：`ContextSession`、`request_context`、`scene-context-service`、`scene-body-generator`（已实现逐场生成 + 合并）。

### A2 生成中按需检索

- 把 `request_context` 真正接入正文循环：模型可在生成前/中请求补上下文，宿主精确检索并计入预算；超限显式报未加载清单。

### A3 预算与覆盖可视化

- 每场记录：注入条目 ID、token、覆盖缺口、请求补充次数，进注入账本；面板可查。

### A4 与协同写作统一

- 协同写作与正文步共用「场景上下文包 + 差异服务」，消除两套注入逻辑。

**A 阶段出口**：截断=0、覆盖率 100%、单章 token 明显下降且人工评分不降。

## 七、依赖与顺序

```
基线采集（1 章）──┐
                 ├→ C1 → C2 → C3 → C4 → C5 ──→ B1 → B2 → B3 → B4 ──→ A1 → A2 → A3 → A4
长期开关（默认关）────────────────────────────┘
```

- C 可在现有真实项目上直接推进（不需要 API）。
- B 需要能跑通一章（需要 API 或已有章节数据）。
- A 需要 B 的校验能力作为循环终止条件。

## 八、风险与回退

| 风险 | 应对 |
|---|---|
| 改动影响生成质量 | 所有行为开关默认关；先量基线再开 |
| 收口写入管道破坏现有流程 | 双轨期：新旧路径并存，开关切换；测试覆盖往返一致性 |
| 校验闭环导致成本上升 | 校验只在高风险项触发修订；设置阈值可调 |
| A 阶段变慢/更耗 token | 场景级循环天然分批；用 token 账本对比；可随时退回单次模式 |
| 大文件改动破坏结构 | 一次只改一个函数/一个文件；先加测试再改 |

## 九、验收门禁（每步都要）

1. `preflight EXIT=0`
2. 新增/更新测试，且关键语义（不静默截断、不丢条目、不猜名字）有断言
3. 指标对比记录在 `docs/design/`（前后数据）
4. 默认关闭的行为开关需在设置页可见、可解释

## 十、不做的事（scope guard）

- 不做多真源并存（不允许"新路径"长期与旧路径并行）
- 不做无指标验证的"优化"
- 不重写 UI/交互（除非阻碍上述目标）
- 不动发布/版本流程

## 十一、立即开工清单（下一轮开始）

1. **基线采集脚本**：真实项目跑一章，导出注入/用量/质量数据（可先手工）。
2. **C1**：短篇/剧本单元写入接 BodyWriter（含版本备份测试）。
3. **C2**：章节状态单一真源 + 一致性测试。
4. 每步提交、`preflight`、记录指标。

## 十二、判断标准（什么时候算"写得好"）

- 客观：截断 0、覆盖率 100%、矛盾/OOC 不增长、修订可收敛。
- 主观：同章同模型，改动后人工评分不低于改动前。
- 只有两者同时满足，才算该阶段完成——这是本计划与之前"功能做完就算完"的根本区别。
