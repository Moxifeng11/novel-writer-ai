# 方案 v4：迭代式上下文装配（ICA）取代一次性注入（2026-11-15）

> 用户决策（本轮）：
> ① LLM OOC 检查成本接受（主角 + 主要配角都走）
> ② 允许插件改写集正文（规范化 `###` 场标题、加场 ID）
> ③ 短篇/剧本与长篇**一视同仁**：每节/每集一文件 + 派生视图
> ④ **一致性约束不设条数上限**：限制条数会造成信息缺失 → OOC。
>   改为**分批、少量多次检索**，判断后再补充（像 harness 的工具循环）

## 一、核心转变：从「一次性预算注入」到「迭代装配」

### 1.1 旧模式（现状 + v2/v3 的局限）

```
收集全部上下文 → 压缩到预算 → 一次性塞进 prompt → 生成
```
无论怎么切分，仍是「一次决定」，超出预算就截断 → 信息缺失 → OOC/矛盾。
限制「3–5 条高风险断言」同样会漏。

### 1.2 新模式：ContextSession 迭代循环

```
锚点（场景卡 + 在场实体 ID + 本章章段）
  ↓
批量加载一批相关事实（按 ID/tag 精确，非模糊）
  ↓
覆盖检查（在场 ID 的必需事实是否齐？断言/关系/伏笔状态/时间线）
  ↓
未齐 → 模型/检查器提出「还缺什么」（结构化 request_context）
  ↓
再加载一批（去重、记账）→ 回到覆盖检查
  ↓
齐了 → 生成；预算触顶 → **显式报未加载清单**，要求缩小场景或分批生成
```

关键原则：

1. **绝不静默截断**：预算不足时返回「还有 N 条未加载（ID 列表）」，由模型决定缩小范围或分批，不允许假装完整
2. **精确检索**：只按 ID / tag / 场景锚命中；模糊/子串不进上下文
3. **可审计**：每一批记录 `{batchId, kind, ids, tokens, reason}` 进注入账本
4. **去重**：已加载 ID 不再重复注入
5. **少量多次**：单批 token 上限小（如 2–3k），多轮累积，避免一次撑爆

## 二、ContextSession 数据结构

```ts
interface ContextSession {
  sceneId: string;                 // 当前场景（PLN/EVT/场景卡）
  anchorIds: string[];             // 在场实体/地点/势力/物品 ID
  chapterSegment: string;          // 本章章段（分卷大纲对应段）
  loaded: Map<string, ContextItem>;// 已加载：key = kind:id
  batches: ContextBatch[];         // 批次记录（审计）
  budget: { usedTokens: number; maxTokens: number };
  coverage: CoverageReport;        // 必需事实覆盖情况
}

interface ContextBatch {
  id: string;
  reason: string;                  // 'anchor' | 'coverage-gap' | 'model-request'
  kinds: ContextKind[];
  ids: string[];
  tokens: number;
  at: number;
}

type ContextKind =
  | 'entity'        // 人物/地点/势力/物品卡
  | 'relation'      // 关系卡（REL-*）
  | 'foreshadow'    // 伏笔条目
  | 'timeline'      // 时间线事件
  | 'setting'       // 设定条目
  | 'worldview'     // 世界观条目
  | 'assertion'     // 一致性断言/事实
  | 'scene'         // 场景卡
  | 'chapter'       // 章节摘要/前情
  | 'rag';          // 知识库检索块
```

## 三、覆盖检查（Coverage Check）

对每个 `anchorId`，计算「必需事实」并核对是否已加载：

| 事实类别 | 必需条件 |
|---|---|
| 实体卡 | 在场每个 ID 的卡（含灵魂层/口吻样本） |
| 关系 | 在场两两之间若存在关系卡 → 必须加载 |
| 伏笔 | `状态 ∈ {planted, progressing}` 且 `涉及在场 ID` 或 `埋设章 ≤ 本章` |
| 时间线 | `章 ≤ 本章` 且 `涉及在场 ID`（或本章所在时间窗） |
| 设定/世界观 | 场景关键词/标签精确命中的条目（命中即全取，不设条数） |
| 断言 | 涉及在场 ID 的**全部高风险断言**（不设条数；分批加载直到齐） |

覆盖报告示例：

```
{ anchor: 'CHR-0001', required: { entity: 1, relation: 3, assertion: 7 }, loaded: { entity: 1, relation: 3, assertion: 5 }, missing: ['AST-0031', 'AST-0044'] }
```

**缺什么补什么，直到 missing 为空**；若预算触顶 → 输出 `unloaded` 清单并要求缩小场景/分批。

## 四、模型侧接口：`request_context` 工具

在 11 步正文/质控/分析、协同写作、短篇节、剧本集都注册同一工具：

```json
{
  "name": "request_context",
  "kind": "read",
  "description": "请求补充上下文：按 ID 或结构化条件精确取（不模糊匹配）。用于发现信息不足时补充，避免凭记忆编造。",
  "parameters": {
    "kind": "entity|relation|foreshadow|timeline|setting|worldview|assertion|scene|chapter",
    "ids": ["CHR-0001", "REL-0003"],
    "filter": { "status": "planted", "inScene": true, "chapterLte": 12 },
    "reason": "为什么需要"
  }
}
```

- 宿主执行：精确检索 → 返回内容 → 记入批次账本 → 更新覆盖
- 模型可多次调用（少量多次），直到不再请求
- 工具结果受 token 预算约束，但**超限会明确告知未返回项**，不是静默截断

## 五、一致性约束注入（不设条数）

- 每场开始时，按在场 ID 拉取**全部**高风险断言（分批）
- 注入形式：约束清单（ID + 一句话约束 + 来源），而不是整份报告
- 生成后：质检用同一批断言做核对（ID 锚定），未通过项进入下一轮修订的补充约束
- 若断言数量极大（如 >100 条），分批注入 + 生成前覆盖检查，**不截断**

## 六、三模式统一

| 模式 | 单元文件 | 场景原子 | 派生视图 |
|---|---|---|---|
| 长篇 | 章节 `CHP-*.md` | 场景卡（Scene 展开 `## 场景N`） | 分卷大纲/看板 |
| 短篇 | 每节 `SEC-*.md` | 节卡（本节目标 5 字段） | 分节大纲派生 |
| 剧本 | 每集 `EP-*.md` | **场卡**（`### N-M`，插件可改写规范化 + 加场 ID）+ 镜卡（分镜 `E01-S01-SH01`） | 分集大纲/分镜表派生 |

三者共用：BodyWriter 落盘、模板体系、`ContextSession`、`request_context`、结算回写管道、质检/一致性检查。

## 八、验收指标（新增/修正）

| 指标 | 目标 |
|---|---|
| 静默截断 | **0 次**（超限必须显式报未加载清单） |
| 在场 ID 覆盖 | 必需事实覆盖 100%（缺项必须有显式记录） |
| 单场景注入 token | 比现状（整章全量）下降 ≥50% |
| 单章总 token | 下降 ≥40%（迭代多批，但每批精确） |
| 截断/重试 | 截断事件 → 0；重试率下降 |
| 一致性矛盾 | 每章矛盾数下降，无新增高危 |
| OOC | 高危 OOC 下降；口吻抽检通过 |
| 回写正确率 | 改名/别名误写 → 0 |
| 迭代轮数 | 记录每场平均批次数（用于调优，不设硬上限） |

## 九、风险与对策

| 风险 | 对策 |
|---|---|
| 迭代轮数过多 → 成本上升 | 单批预算小 + 覆盖检查尽早收敛；记录轮数；对简单场景跳过补充 |
| 模型滥用 request_context | 工具结果计入预算、单场最大轮数可配置（默认 6）、超限要求缩小场景 |
| 精确检索依赖 ID 完整 | B 阶段迁移必须先完成（补 ID + 登记表校验） |
| 剧本改写正文风险 | 只规范化场标题与加场 ID，正文内容不动；改写前存版本（BodyWriter 备份） |
| 覆盖检查误判「已齐」 | 断言/关系按 ID 计数核对，缺项写显式记录，质检复核 |
