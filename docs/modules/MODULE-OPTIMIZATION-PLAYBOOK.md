# 模块化优化开发制度（MODULE-OPTIMIZATION-PLAYBOOK）

> 状态：活跃 · 2026-11-17
> 版本：1.0（2026-11-16 建立）
> 适用范围：所有「一个模块一个模块打磨」的迭代（设置页各分区、写作工作台、规划、设定、正文、统计、桌宠、MCP、市场等）
> 配套文件：模块清单 `docs/modules/INDEX.md`、模块页模板 `docs/modules/_TEMPLATE.md`、任务板 `scripts/board.mjs`、交接快照 `scripts/handoff.mjs`

---

## 一、目的

过去按「问题驱动」改代码：用户报一个、修一个，容易出现三种问题：

1. 只修了看得见的点，模块内部语义仍然混乱（例：API 配置里「启用」被当成「切换」）；
2. 改动缺少模块级验收标准，过几轮又退化；
3. 没有统一的记录位置，下一轮（或另一个 Agent）要重新摸一遍现状。

本制度把「模块」作为迭代单位：**每个模块先定义边界与验收标准，再按固定流程优化，每轮都留下可复用的现状页和验证记录。**

---

## 二、角色与职责

| 角色 | 职责 | 产出 |
| --- | --- | --- |
| 用户（作者） | 决定优先级与取舍；验收体验；对「是否值得做」拍板 | 模块目标、体验反馈、放行/打回 |
| 主 Agent（当前会话 Owner） | 盘点模块现状、拆问题、实现、自测、门禁、记录、提交 | 模块页、提交、验证记录、交接 |
| 协作 Agent（ZCode / Trae） | 按任务板领取独立任务；只改自己 scope | 任务证据 + commit |
| 任务板 | 派发/认领/完成状态，写范围锁 | `.trae/tasks` 状态、`board.mjs` 输出 |
| 交接快照 | 三方唯一进度来源 | `PROJECT-RULES.md` 的 HANDOFF 块 |

原则：**用户只做决策和验收，不替 Agent 记现状**；Agent 必须自己维护模块页和验证记录。

---

## 三、模块边界

1. 模块 = 用户能感知的一个功能面（不是单个文件）。一个模块通常跨 `ui/` + `core/` + `shared/` + `engine/`。
2. 每个模块在 `docs/modules/<module>.md` 有一页，写清：入口、数据、关键规则、当前状态、问题清单、验收记录。
3. 跨模块共享逻辑放 `shared/`，并单独给单测；模块页只引用，不复制。
4. 模块清单在 `docs/modules/INDEX.md` 维护；新模块先登记再开工。

---

## 四、单模块迭代七步法

每轮迭代必须按顺序走完，前一步的产出是后一步的输入。

### 第 1 步：盘点现状（Audit）
- 读代码入口 + 数据字段 + 现有测试 + 用户反馈；
- 产出一段「现状事实」：现在怎么工作、数据存哪、哪些语义是错的；
- **必须做一次实机观察**（打开设置页/界面截图或 DOM 校验），不能只读代码下结论；
- 记录到模块页「现状」小节。

### 第 2 步：问题清单（Issue List）
- 把用户反馈拆成可验收的条目，编号 `M-01...`；
- 每条标 P0/P1/P2（定义见第五节）+ 期望行为 + 影响面；
- 写进模块页「问题清单」，勾选状态随进度更新；
- 不确定的取舍列「待用户确认」，不要自己埋掉。

### 第 3 步：模块 Brief（设计）
- 一句话目标：这轮要让这个模块达到什么状态；
- 范围：改哪些文件/数据字段，不改什么（防止顺手改别的模块）；
- 数据与迁移：新字段默认值、旧数据怎么办、切换/回滚表现；
- 验收标准：可观察到的事实（不是「优化了体验」这种话）；
- 需要用户确认的点单独列出。

### 第 4 步：实现（小步）
- 先数据/纯逻辑（带单测），再 UI 接线；
- 每个可独立验证的单元一次提交；不攒大提交；
- 遵守第七节 UI 规范与第八节数据规范。

### 第 5 步：验证矩阵（必须全绿）
| 层级 | 做什么 | 证据 |
| --- | --- | --- |
| 纯逻辑 | 新增/修改的 shared 逻辑单测 | `vitest run <file>` 通过数 |
| 组件/DOM | 设置页/弹窗假 DOM 渲染测试 | 测试文件 + 断言文案 |
| 回归 | 受影响模块的既有测试 | `preflight` 全量 |
| 实机 | Obsidian 内真实触发（reload + eval/DOM 检查） | 关键状态/文案/截图 |
| 门禁 | `npm run preflight` | EXIT=0 |
| 文档 | 模块页 + planning 记录 + `gen:docs` | 提交内含 |

### 第 6 步：记录（Documentation）
- 更新模块页：状态、已解决项、验证记录、剩余问题；
- 更新 `docs/planning/` 里当前轮的记录（有取舍/踩坑必须写）；
- 需要时更新 `docs/README.md` 索引。

### 第 7 步：提交与交接
- 提交信息格式见第九节；
- `git push`（放行）；tag/Release 必须用户明确同意；
- 更新 handoff 快照；任务板任务标记 done/fail。

---

## 五、问题分级与红线

| 级别 | 定义 | 处理 |
| --- | --- | --- |
| P0 | 数据丢失/安全/模块不可用/误导性状态 | 本轮必做，做完立即验证 |
| P1 | 明显体验问题或语义错误（用户会反复踩） | 本轮必做 |
| P2 | 打磨项（密度、文案、动效、边角） | 本轮可做则做，否则进 backlog |
| P3 | 想法/未来能力 | 只记录，不排期 |

红线（任何模块迭代都不许碰）：
- 不删用户数据；迁移必须幂等、可逆或至少保留旧值出处；
- 不悄悄上调 bundle/CSS 基线；必须 `--update-baseline --note` 写明原因；
- 不破坏既有测试来「让门禁变绿」；测试断言要跟着**新语义**改，并说明语义变更；
- 不改历史提交（不 rebase/amend 已推送提交）；
- tag/Release 必须用户明确确认。

## 六、Definition of Done（模块验收清单）

一个模块的一轮优化只有全部勾选才算完成：

- [ ] 模块页「现状/问题清单/验收记录」已更新
- [ ] 用户反馈的 P0/P1 全部关闭，P2 有明确去向
- [ ] 纯逻辑有单测；UI 有 DOM/渲染测试（或说明为何不适用）
- [ ] 实机观察过：默认态、空态、错误态、暗色/窄面板、切换/重载后状态
- [ ] 数据字段有默认值 + 旧数据迁移（或明确说明不涉及）
- [ ] `npm run preflight` EXIT=0
- [ ] 提交信息含「改了什么/为什么/验证」
- [ ] handoff 更新；任务板任务已 done

## 七、UI 规范（参考 zcode 交互）

1. **行内优先**：能行内改的不要弹窗；「添加/编辑」做成行内表单或展开行。
2. **即改即存**：开关/下拉/输入失焦即保存；失败要有可见提示（Notice），不能静默。
3. **折叠分组**：长页面按用途折叠（渠道配置 / 全局分配 / 任务参数），默认收起低频项。
4. **状态分离**：「当前使用」和「是否显示」是两件事，UI 上必须有不同控件与文案。
5. **状态可见**：列表行要能一眼看出当前项、模型摘要、隐藏/停用状态。
6. **空态与失败态**：空列表给下一步动作；失败给原因 + 恢复路径。
7. **窄面板优先**：设置面板常 300–400px 宽，避免横向滚动和长单行输入。
8. **暗色/弹窗兼容**：只用 Obsidian CSS 变量取色；弹层/设置窗口用 `activeDocument` 与所属窗口的 `doc`。

---

## 八、数据与迁移规范

1. 新字段必须可选 + 有默认值；读取处用 `?? 默认` 兜底，避免旧 data.json 崩溃。
2. 迁移函数必须幂等：重复执行不重复写、不重复加。
3. 「每渠道各自记住」的数据用 `Record<providerId, ...>`，切换时保存旧、恢复新；不要直接重置成默认。
4. 用户可见的大体积数据（图片等）落独立文件，`data.json` 只存元数据。
5. 迁移失败不许静默丢配置：至少保留旧字段并在日志/Notice 说明。

---

## 九、提交与变更规范

**提交信息模板**：

```
<type>(<module>): <一句话结果>

问题：
- <用户可见现象>
原因/现状：
- <代码/数据层事实>
改动：
- <条目>
验证：
- preflight EXIT=0（N 测试）；实机：<关键操作与结果>
```

- `type`：`feat` / `fix` / `refactor` / `perf` / `docs` / `chore`
- 一个提交只做一件事；跨模块改动拆开。
- 版本号只在用户确认发布时改；日常迭代保持 `package.json` 版本不变。
- 门禁顺序：`gen:docs`（有新源码/文档）→ 必要时更新 bundle/css 基线（带 note）→ `preflight`。

---

## 十、记录模板

见 `docs/modules/_TEMPLATE.md`；模块页必须包含：定位、数据、现状、问题清单（含分级与状态）、验收记录（日期 + 操作 + 结果）、关键决策、测试清单、剩余 backlog。

每轮结束在 `docs/planning/<当前焦点>.md` 追加一节：用户诉求 → 做了什么 → 验证 → 没做什么/为什么。

---

## 十一、迭代节奏

1. 每轮**只专注一个模块**（可带一个相邻小修）。
2. 开工前在模块页写下本轮 Brief（第 3 步），结束前写验收记录（第 6 步）。
3. 用户验收不通过 → 回到第 2 步补问题清单，不直接改代码。
4. 模块达到「DoD 全绿 + 用户确认体验 OK」后标记 `stable`，转入低维护；下一模块按 `docs/modules/INDEX.md` 顺序推进。
5. 每完成 2–3 个模块，做一次跨模块回归（preflight 全量 + 主流程实测）。

---

## 十二、命令速查

```bash
# 单测
npx vitest run tests/unit/<path>.test.ts

# 门禁（提交前必须）
npm run gen:docs
npm run preflight

# 基线（仅在体积确有变化时，且必须写 note）
node scripts/check-bundle.mjs --update-baseline --note "<原因>"
npm run css:baseline

# 实机
obsidian plugin:reload id=novel-writer-ai
obsidian eval code="..."

# 交接 / 任务板
node scripts/handoff.mjs --from dsh --stage ... --delivered ... --doing ... --next-zcode ... --next-trae ... --next-dsh ... --ask ...
node scripts/board.mjs next --me dsh
```
