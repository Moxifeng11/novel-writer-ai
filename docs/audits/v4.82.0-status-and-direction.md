## 五、方向决策

### 5.1 我的判断：停止堆功能，转向"可验证性 + 容量治理"

理由三条：

1. **功能侧已无待补代码**。v5 闭环、G1–G7 全 done、安全 r3 只剩 P3 的 Agent 边界问题。继续加功能会直接撞上两个硬墙：包体积 0.7% 余量和 UI 覆盖率 9.7%。
2. **37% 的代码没有自动化保障**。UI 层 90,418 行里绝大多数改动只能靠人工点击发现回归。这是当前最大的"下一版会出事的概率"来源。
3. **自设目标已经写在 ROADMAP 里但没兑现**（0 覆盖文件 ≤40、main.js ≤5MB）。不补这两项，后面每加一个功能都要先付一次体积税。

### 5.2 建议的三条主线（按优先级）

#### 主线 A｜UI 可测性（最高优先）

不追求"给视图补覆盖率"，而是**把 UI 里能抽的纯逻辑抽出来**，用三条低成本杠杆：

| 动作 | 预期收益 |
|---|---|
| A1. 对 `ui/views/` 整层（1.42%）做"抽纯函数"扫描：把 2,000+ 行视图里的判定/格式化/状态机移到 `ui/<feature>/` 并可单测 | 每条抽出通常 +15~40 用例，覆盖率提升最快 |
| A2. 优先处理**零覆盖且超 1,000 行**的文件：`book-detail-renderer.ts`（2,247 行 / 0.1% / 无测试） | 单文件即为最大空缺 |
| A3. 建立"视图层测试下限"门禁：新视图/大改视图必须带 ≥1 个行为测试（避免继续裸奔） | 阻止债务继续增长 |

**不建议**去追 UI 整体覆盖率数字（DOM 渲染测试性价比低）；应追"**0 覆盖文件数 83 → ≤40**"这个 ROADMAP 既定指标。

#### 主线 B｜包体积治理（与 A 并列，有硬截止）

`main.js` 只剩 35,469 B 余量。

| 动作 | 预期收益 |
|---|---|
| B1. 审计 `shared/changelog-data.ts`（2,343 行，纯文案）——内置 CHANGELOG 随版本线性增长，是包体积的持续负担 | 改为主包只留最近 3~4 版，历史版按需从 GitHub 拉取或独立文件；**可释放数十 KB** |
| B2. 评估 `assets/template-scaffold`（56 个模板已嵌入 bundle） | 若要再省，可改为首次运行按需生成 |
| B3. 补充 `check:bundle` 的"净增预算"（现在只校验总量，不校验单批增量） | 让每次提交都看见体积代价 |

> B1 是我最推荐的单点：changelog 是纯展示数据，占着运行时体积却只在"更新日志"弹窗用一次。

#### 主线 C｜收尾剩余安全债

S3-17~S3-21 五项 P3 全部集中在 **Agent 权限边界**（move_file / spill / 恢复快照 / 重定向 / 文件名净化）。这批与主线 A/B 无冲突，可以作为一个独立小批次（约 1~2 轮）收掉，让安全审计维度真正归零。

### 5.3 不建议做的事

| 不做 | 原因 |
|---|---|
| 继续按行数切片 `co-writing-view.ts` | 2026-11-06 已拍板停止：切片对 bundle 是**净增**（三次累计 +3,664B），主指标已改为 net-bundle |
| 追整体覆盖率到 60%+ | UI DOM 测试性价比低，会把人力拖进 mock 泥潭 |
| 一次性重构 deconstructor 三件套 | 每个 2,500~3,600 行，无测试护网时重构风险高于收益；应先补测试再谈拆分 |
| 在余量 0.7% 时继续加功能 | 会立刻顶破 5 MB 自设上限 |

### 5.4 建议的排期

| 轮次 | 内容 | 交付标准 |
|---|---|---|
| 第 1–2 轮 | **B1 包体积治理**（changelog 拆分/按需化） | `main.js` 回落至 ≥100KB 余量；preflight 全绿 |
| 第 3–5 轮 | **A2 + A1**：`book-detail-renderer` 抽纯函数 + `ui/views` 零覆盖文件治理 | 0 覆盖文件数下降 ≥20 个；新增 ≥60 用例 |
| 第 6 轮 | **C**：S3-17~S3-21 收尾 | 安全 r3 21/21 归零（除 S3-5 上游依赖） |
| 第 7 轮 | **A3 门禁**：视图层测试下限 | 新门禁入 preflight |
| 第 8 轮 | 版本节点 v4.83.0 + Release | 保守发布，标注治理成果 |
