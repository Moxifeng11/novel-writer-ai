## 二、AI 参数体系（第三轮新挖）

### 2.1 三档温度分工（关键设计）

云笔**不是**一个温度走天下，而是按任务性质分三档：

| 温度 | 用途 | 证据 |
| ---: | --- | --- |
| **0.3** | 质量自检 / 结构化输出 | `temperature:.3` 用于「发送流式AI请求」的质量自检环节，配 24 万 ms 超时 |
| **0.6** | 指令优化 / 轻改写 | `temperature:.6, max_tokens:1024`，系统提示为「AI 指令优化专家」 |
| **0.8** | 内容生成 / 创意写作 | `temperature:.8` 用于正文生成与优化建议流式输出 |

**为什么这个分工重要**：
- 结构化输出（JSON）要低温度——高温度会导致格式漂移、字段缺失
- 创意写作要高温度——低温度产出保守、重复
- 中间档用于「保持原意但要更清晰」的改写任务

### 2.2 max_tokens 分档

| 值 | 用途 |
| ---: | --- |
| 1024 | 指令优化（短输出） |
| 4096 | 质量自检报告 / 章节摘要 |
| 8192 | 单章正文（默认） |
| 16384 | 长章 / 批量完善 |

### 2.3 推理强度（thinking 模式）

四档：`low` / `medium`（默认）/ `high` / `max`

对应的 thinking budget：
```js
const budget = { low: 8192, medium: 16384, high: 32768, max: 65536 };
```

**注意**：`max` 档会映射为 API 的 `high`（因为部分 provider 不认 `max`）。
另有 `Cd(model)` 判断——某些模型显式 `thinking: { type: 'disabled' }`。

### 2.4 本仓现状对照（机会点）

| 维度 | 云笔 | 本仓 | 差距 |
| --- | --- | --- | --- |
| 温度 | **3 档按任务分工** | **0.7/1.4/1.25 三值并存且未按任务分工**（API层0.7、步骤链1.4、协同1.25） | ⚠️ **更需统一** |
| max_tokens | 4 档（1024/4096/8192/16384） | 有配置但未分档 | ⚠️ |
| 推理强度 | 4 档 + 模型能力判断 | 无 | ❌ 缺 |

**这是本轮最有价值的发现**：本仓温度不仅「一值管所有任务」，而且有**三个不同默认值**
（API 层 0.7 / 步骤链 1.4 / 协同 1.25）。质量自检要稳定 JSON、正文生成要创意，
共用一个值必然有一端不最优；1.4 更是超出多数模型的建议上限。

## 三、AI 通道架构（第三轮新挖）

### 3.1 双通道设计

```js
// 云端直连（前端直接 fetch 到 provider）
async function ue(Ge, Fe, Et, ht) {
  if (isGemini(Fe)) { /* Gemini 专用 SSE 端点 */ }
  const res = await fetch(Fe._端点URL + Fe._请求路径, {
    headers: { Authorization: `Bearer ${Fe._API密钥}`, ...custom },
    body: JSON.stringify(Te(Ge, Fe)),   // ← 请求体在前端组装
  });
}

// 本地代理（走后端转发，用于隐藏密钥）
async function he(Ge, Fe, Et, ht) {
  const res = await fetch("/api/ai/local/stream", {
    body: JSON.stringify({
      端点URL, API密钥, 请求路径, 自定义请求头,
      请求体: Te(Ge, Fe),
    }),
  });
}
```

**两条通道都支持流式**（SSE 解析 + 60 秒无数据超时）。

**关键点**：无论走哪条，**请求体都在前端组装**——这是它能被逆向的根本原因。

### 3.2 流式协议细节

```js
const TIMEOUT_MS = 60_000;   // 60 秒未收到数据即判超时
// 解析：按行切，只处理 "data: " 前缀
// 提取：choices[0].delta.content / delta.tool_calls / finish_reason
```

**工具调用被流式支持**（`delta.tool_calls`）——说明它的 Agent 能力是流式的，
不是等完整响应再解析。

### 3.3 Provider 画像

`/api/ai/status` 返回的 provider 清单（含每个模型的能力标记）：

| Provider | 代表模型 | 上下文 | 最大输出 | 工具调用 | 思考模式 |
| --- | --- | ---: | ---: | --- | --- |
| deepseek | deepseek-chat | 64000 | 8192 | ✅ | ❌ |
| deepseek | deepseek-reasoner | 64000 | 8192 | ✅ | ✅ |
| doubao | doubao-seed-2-0-pro | 256000 | 32000 | ✅ | ✅ |
| doubao | doubao-seed-2-0-lite | 256000 | 32000 | ✅ | ✅ |
| qwen | qwen-plus | 131072 | 8000 | ✅ | ❌ |

**默认是 doubao-seed-2-0-lite**（全站默认，标注「轻量高性价比」）。

**能力标记的用途**：`支持思考模式` 决定要不要传 `thinking` 参数；
`支持工具调用` 决定能不能挂 Skill 工具。这是**运行时能力探测**，不是硬编码。

## 四、Skill 全量清单（第三轮确认）

只有 3 个，但每个都很重：

| id | 名称 | 挂载工具 | 提示词长度 | 定位 |

## 六、端到端链路（三轮调研汇总）

```
① 用户通过「探讨模式」11 步填框架
   ↓ 每步有引导话术 + 输入占位 + 快速想法（降低门槛）
② 写入数据层（36 字段章节蓝图 / 实体库 / 时间线）
   ↓ 或走 CreateProjectSkill 的 14 步三段式门禁（AI 执行）
③ 正文生成：组装 32 个上下文模块
   ↓ 温度 0.8，max_tokens 8192，推理 medium
   ↓ system 段：基础 → 文风 → L0-L3 → 铁律1-9 → 技法 → 协议行
   ↓ user 段：世界观→角色→场景→…→前章原文→注意力锚点→动笔提醒
④ LLM 生成（走 local/stream 或直连，SSE 流式）
   ↓
⑤ 前端清洗 <think>/<writing_plan>/<quality_check>
   ↓
⑥ 蒸馏（温度 0.3）：17 项提取 → 回写大纲字段
   ↓ 双向补写：回填上一章章尾悬念 + 下一章章首衔接
⑦ 质量自检（温度 0.3）：四维自检
   ↓
⑧ 用户「采用」→ 落库
```

**三个温度点**分散在 ③⑥⑦ 三步：生成用 0.8、蒸馏用 0.3、自检用 0.3。

## 八、调研方法论记录（避免以后重复踩坑）

| 坑 | 教训 |
| --- | --- |
| 模块数算成 29（实际 32） | `预估tokens:3e3` 科学计数法导致正则 `\d+` 失配 |
| 11 步探讨模式混同 14 步 SOP | 一个是前端 UI，一个是 Agent Skill |
| 长句被当成「唯一缺口」 | 只和基线比、没做相关性分析，且落在单章方差内 |
| 「抽屉无宽度规范」 | Modal 早有规范（`--nw-modal-*` + v8.3 类），只缺抽屉部分 |
| 「本仓无 -rgb 色变体」 | 实际在用 `rgba(var(--interactive-accent-rgb), 0.1)` |

**统一教训**：任何「云笔有 N 个 X」或「本仓缺 Y」的断言，必须 grep/重新计数到证据，
不能靠印象或单次测量。
