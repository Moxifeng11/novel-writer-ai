## 一、先自查：找到三处幻觉

用户提醒「以免造成幻觉」是对的。复核后发现前作有三处不准确：

### 幻觉 1：模块数是 32 个，不是 29 个

| | 前作 | 实际 |
| --- | --- | --- |
| 模块总数 | 29 个 | **32 个** |
| 普通模式 | 27 个 / 16250 tokens | **30 个 / 23250 tokens** |
| 专注模式 | 7 个 / 3750 tokens | 7 个 / 3750 tokens（这个对） |

**漏算的 3 个**：`narrative_rules`（叙事铁律 3000t）、`writing_techniques`（文笔技法 2000t）、
`characters`（角色列表 2000t）。

**为什么会漏**：这三个的 `预估tokens` 值是 `3e3` / `2e3` 这种科学计数法，
我的正则 `\d+` 匹配不到，整个对象被跳过。

**影响**：普通模式实际是 **23250 tokens**，比前作说的多 7000。
这个数字很重要——它说明云笔单次正文生成要吃掉 2.3 万 tokens 上下文。

### 幻觉 2：11 步探讨模式 ≠ 14 步建项目 SOP（两套东西）

前作把这两者混在一起讲，实际是**两个独立系统**：

| | 11 步探讨模式 | 14 步建项目 Skill |
| --- | --- | --- |
| 位置 | **前端 UI**（`Yr` + `ol` schema） | **Agent Skill**（挂载 14 个工具） |
| 交互 | 用户在侧边栏逐步点选/输入 | AI 按 SOP 自动执行，中途 `agent_ask_user` |
| 产出 | 直接写入项目各模块 | 同上，但走三段式门禁 |
| 前端有引导话术 | ✅ 每步有「引导说明/输入占位/快速想法」 | ❌ 无 UI |
| 依赖 | 前置依赖链（如情节脉络依赖前 9 步全部） | 顺序 14 步 |

**为什么容易混**：两者最终写入同一批数据表（世界观/角色/势力…），
但**一个是人操作的 UI，一个是 AI 执行的 SOP**。

### 幻觉 3：「三处段落规则打架」——body-format 早已收敛（前文已更正）

这个在优化方案文档里已更正过，此处记录一笔：`shared/body-format.ts`
文件头注释明确写着 5 套契约在 2026-10-20 已收敛为 `deriveBodyFormat()` 单源。

## 二、实际前端设计（这部分前作完全没碰）

### 2.1 抽屉面板：33 个，宽度分 6 档

这是云笔前端最核心的信息架构——**一切编辑都在右侧抽屉里完成，不跳页**。

| 宽度 | 档位含义 | 面板 |
| ---: | --- | --- |
| **560px** | 管理类（列表+详情+操作） | 功法体系 / 特殊设定 / 已历事件 / 资产管理 / 伏笔管理 |
| **520px** | 主数据类 | 势力阵营 / 故事核心 / 货币体系 / 物品列表 / 力量体系 / 大纲设定 / 角色管理 / 人物关系 / 大纲编辑 / 时间线 / AI完善 |
| **480px** | 辅助类 | 世界观 / 地理地图 / 伏笔AI / 情节脉络 / 情节AI / 情节完善 / 支线故事 / AI生成 |
| **450px** | 只读详情 | 大纲详情 |
| **420px** | 单条编辑 | 功法编辑 / 力量编辑 / 特殊设定编辑 / 伏笔编辑 / 情节编辑 |
| **380px** | 轻详情 | 势力详情 / AI角色生成 |
| **320px** | 常驻助手 | AI助手 |

**设计语言解读**：
- `560 = 管理`（要放列表 + 表单 + 按钮，最宽）
- `520 = 主数据`（列表为主）
- `480 = 辅助`（内容为主）
- `420 = 编辑`（单个对象）
- `380 = 详情`（只读）
- `320 = 助手`（常驻，最窄）

**全部可拖拽**，clamp 范围 `280~600` / `360~800` / `400~900` / `450~950` / `320~800`
（不同面板上限不同，宽面板可拖到 900–950）。

**本仓对照**：本仓的 Modal / 侧边栏是否有这种统一宽度语义？
如果没有，会出现「同一个功能在不同地方宽度不同」的割裂感。

### 2.2 三栏工作台布局

```
┌────────────┬──────────────────────────┬────────────┐
│  左侧栏     │      中间画布/编辑器        │  右侧属性面板 │
│  树/列表    │      （可视化编辑）        │  （详情/编辑） │
│  可拖拽     │                          │  可折叠      │
└────────────┴──────────────────────────┴────────────┘
         ↑ 拖拽手柄                       ↑ 悬浮按钮组
```

**左侧栏**：树形导航（如「🌳 地点层级」，用 `paddingLeft = 层级*16+8` 做缩进）
**中间**：画布编辑器（支持层级/网络两种布局模式，滚轮缩放、锚点连线、右键设父子）
**右侧**：属性面板，可 `面板折叠`
**悬浮按钮组**：生成历史 / AI生成 / 最大化 / 展开属性 / 关闭（5 个，垂直排列）

**操作提示直接写在 UI 上**：`"拖拽节点移动 · 滚轮缩放 · 锚点连线 · 右键设父子"`

### 2.3 设计 token：30 个 CSS 变量，三层层级

```css
/* 背景层级（4 层，从深到浅）*/
--bg-darker → --bg-dark → --bg → --bg-lighter → --bg-card → --bg-hover

/* 主色 */
--primary / --primary-hover / --primary-dark / --primary-color
/* 语义色 */
--success / --warning / --error / --info  (+ 各自的 -rgb 变体)
/* 文字层级（3 层）*/
--text / --text-primary / --text-secondary / --text-tertiary
```

**关键设计**：每个语义色都有 `-rgb` 变体（`--primary-rgb: 99 102 241`），
用于 `rgb(var(--primary-rgb) / 0.1)` 做透明度叠加。这是深色主题的常见做法。

**本仓对照**：本仓 `styles-src/` 是否也有 `-rgb` 变体？
如果没有，做半透明背景时会写死颜色，主题切换会断。

### 2.4 图标体系：Remix Icon（565 个不重复图标）

| 族 | 数量 |
| --- | ---: |
| ri-arrow-* | 20 |
| ri-file-* | 19 |
| ri-user-* | 16 |
| ri-chat-* | 14 |
| ri-map-* / ri-shield-* / ri-checkbox-* / ri-folder-* | 各 8 |
| ri-book-* | 7 |

**565 个图标**说明它不画自己的 SVG，全靠 Remix Icon 生态。
好处：一致性强、体积小（字体/按需引入）。坏处：图标辨识度平庸。

### 2.5 动画体系：13 种过渡

```
fade / fade-slide / panel-fade / preview-fade
slide / slide-down / slide-up / slide-right / slide-in / slide-panel / slide-detail
scale / expand
```

**按语义命名**（不是 `transition-1` 这种），说明设计师有明确的动效语言：
- `slide-panel` 抽屉进出
- `slide-detail` 详情展开
- `panel-fade` 面板淡入

### 2.6 Toast 通知：4 类，时长分级

| 类型 | 出现次数 | 典型时长 |
| --- | ---: | --- |
| success | 8 | 3000ms |
| warning | 4 | 4000ms |
| error | 1 | 4000ms |
| info | 1 | 3000ms |

**错误的显示时间比成功长**（4000 vs 3000）——给用户更多时间读错误。细节到位。

### 2.7 进度文案：直接暴露内部步骤

这是我最意外的一点——云笔**把内部步骤名直接展示给用户**：

```
正在加载上下文...
正在构建生成提示词...
章节大纲完善完成，继续生成正文...
正在分析正文内容...
检测新角色并生成人生经历...
正在加载事件线数据...
正在加载主角事件线...
正在加载支线事件流...
正在加载章节事件流数据...
```

**为什么这是好设计**：
- AI 生成要几十秒，不显示进度用户会以为卡死
- 显示「正在加载主角事件线」比「加载中...」更能建立信任
- 也暴露了它的内部流程——**这也是我们能逆向出来的原因之一**

**本仓对照**：本仓的生成进度是否也只显示「生成中...」？
如果是，改成具体步骤名能显著提升体感。

### 2.8 生成结果面板的四态

| 状态 | UI 表现 |
| --- | --- |
| 生成中 | `正在生成` + `流式内容`（实时显示） |
| 完成待确认 | `生成完成，请确认是否采用` + 采用按钮 |
| 失败 | `解析生成结果失败，请重试` + 重试按钮 |
| 已取消 | `已取消生成` |

**核心是「完成待确认」这一态**——生成结果不直接落库，要用户点了才写。
这是防 AI 乱改数据的关键设计。

## 三、其他「还有一些东西」（前作漏掉的机制）

### 3.1 协议行输出（CR/CI/NE/BT）

云笔在正文末尾要求模型输出结构化行：

| 前缀 | 含义 |
| --- | --- |
| `CR` | 角色关系变化 |
| `CI` | 物品变动 |
| `NE` | 新实体（违反实体边界时会标出） |
| `BT` | 境界突破 |

**作用**：正文是散文，但关系/物品/境界变化需要结构化落库。
让模型在正文后追加这几行，后端解析后更新数据表。

**这解决了一个真问题**：本仓的「角色关系/物品/境界」变化是从正文里再抽一次（distill），
云笔是让模型**写的时候顺便输出**——少一次 LLM 调用，且准确率更高（模型自己知道改了什么）。

### 3.2 输出清洗：三种思考标签

```js
function Py(t) {
  // 剥掉 <think>、<writing_plan>、<quality_check>
}
```

模型可能输出思考过程，前端统一剥离。**注意它也剥 `writing_plan` 和 `quality_check`**——
说明它会让模型先写计划再写正文，然后把计划删掉。

**本仓对照**：本仓是否有同类清洗？（`shared/api-response-utils.ts` 里有 `stripThinkingBlock`）
但 `writing_plan` / `quality_check` 这类自定义标签是否覆盖？

### 3.3 模态与任务的分离

云笔有 `agent_plan_create` / `agent_plan_progress` / `agent_ask_user` 三个工具，
构成「AI 执行长流程」的基础设施：

- `agent_plan_create`：声明要做 14 步，当前在第几步
- `agent_plan_progress`：推进步骤
- `agent_ask_user`：**真暂停**等用户回答（不是假装暂停）

**「真暂停」是关键**。前作提到这个但没强调：
它要求「严禁纯文本提问后结束轮次（驱动器会续跑致草案重复）」——
说明它踩过「模型假装提问但自己继续跑」的坑。

**本仓对照**：本仓的步骤链是自动跑的，没有「真暂停」机制。

### 3.4 快捷预设（3 个，前作提过但要补细节）

| 预设 | 模块组合 | 用途 |
| --- | --- | --- |
| 极简续写 | core_identity + content_filter + perspective | 最大化专注力（3 个模块，550t） |
| 角色聚焦 | + characters + story_core | 对话密集章（5 个模块，2850t） |
| 世界观聚焦 | + worldview + power_system + scene_geo + characters | 设定密集章（7 个模块，4300t） |

**与专注模式的区别**：专注模式是「7 个固定模块」，预设是「按场景选不同组合」。
说明云笔认为**不同章节类型需要不同上下文**。

### 3.5 强制补齐机制（版本迁移）

```js
const o7 = ["prev_chapter_text","next_chapter_constraint","connection_check","pre_writing_reminder"];
// 版本升级时强制把这三个模块加进用户的自定义列表
```

即使用户自定义精简模块，**衔接三件套 + 动笔提醒永远强制**。
而且有版本号（`mb=2`）做迁移——老用户配置会被自动补上。

## 五、11 步探讨模式完整 schema（前端 UI）

| # | 步骤 | 区块 | 字段数 | 模式 | 前置依赖 |
| --- | --- | --- | ---: | --- | --- |
| 1 | 开篇 | 基本信息 | 5 | 单条 | 无 |
| 2 | 世界观 | 世界观 | **19** | 单条 | 基本信息 |
| 3 | 主角身份 | 角色 | 13 | 多条 | 基本信息, 世界观 |
| 4 | 金手指 | 特殊设定 | 13 | 多条 | 基本信息, 世界观, 角色 |
| 5 | 核心冲突 | 故事核心 | 6 | 单条 | 基本信息, 世界观, 角色, 特殊设定 |
| 6 | 势力阵营 | 势力阵营 | 10 | 多条 | 世界观, 故事核心, 角色, 特殊设定 |
| 7 | 力量体系 | 力量体系 | 12 | 多条 | 世界观, 特殊设定 |
| 8 | 货币体系 | 货币体系 | 9 | 多条 | 世界观, 力量体系, 势力阵营 |
| 9 | 地图 | 地图 | 5 | 多条 | 世界观, 势力阵营, 角色 |
| 10 | 情节脉络 | 情节脉络 | 9 | 多条 | **前 9 步全部** |
| 11 | 自由讨论 | — | 0 | 扩展 | 基本信息…情节脉络 |

**每步都带三样东西**（这是前端设计的精华）：
1. **引导说明** — 告诉用户这一步要决定什么
2. **输入占位** — 给一个具体例子（「例：我想写一本 300 万字的东方玄幻爽文…」）
3. **快速想法** — 4 个可一键点的方向（「东方玄幻爽文，男频成人，复仇逆袭」…）

**为什么这套有效**：用户不需要懂「世界观该填哪些字段」，
只需回答「你想写什么」，AI 按 19 个字段展开。**降低填写门槛**。

**世界观 19 个字段**（最复杂的一步）：
世界名称/类型/时代背景/核心规则/地理环境/社会结构/历史背景/特殊元素/主要冲突/势力格局
+ **历法 9 项**（历法名称/纪年体系/故事起点日期/每年月数/每月天数/每日时辰数/时辰名称/时长模板/显示格式）

**注意**：历法是在世界观步骤里一起定的——因为时间线需要它。
这个设计很清醒：**先定历法，后面所有时间标注才有依据**。

## 九、方法论：这次是怎么避免幻觉的

用户明确要求「以免造成幻觉」。这次的做法：

1. **先自查前作**，找到 3 处数据错误（模块数、11步vs14步、契约冲突）
2. **写「待核实清单」**，把所有「本仓现状」断言列出来
3. **逐条 grep 核实**，结果 3 项猜错
4. **据实修正建议清单**，从 9 条砍到 3 条

**教训**：任何「本仓有/没有 X」的断言，必须先 grep 到证据。
任何「云笔有 N 个 X」的断言，必须从原始数据重新计数（不能信自己的正则）。

**这次的 regex 教训**：`预估tokens:3e3` 这种科学计数法导致漏算 3 个模块。
以后提取结构化数据要先抽样验证各级字段的取值形态。
