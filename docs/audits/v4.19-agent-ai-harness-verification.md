# v4.19 对话 Agent 接入 AI Harness 验证

- 日期：2026-10-28
- 版本：4.19.0（本地工作树）
- 范围：对话引导 Agent 从纯规则流程升级为 DeepSeek Harness 架构的真 AI 对话（模型 + 工具循环），保留离线规则引擎兜底

## 一、问题：Agent 完全没接入 AI

改造前的「对话引导」只有一个 AI 触点：`aiParse`（自由文本槽位解析），且只在用户输入匹配不上 chips 时才触发。其余全部回复（欢迎语、路径引导、设定摘要、创建确认）都是 `conversation-engine.ts` 里写死的静态字符串——用户看到的「对话」实际上是固定流程脚本换皮。

## 二、DeepSeek Harness 源码研究与移植决策

下载 `deepseek-ai/deepseek-harness`（master 分支，"Everything is a Plugin"，Cordis 架构）源码研究。其核心组件与移植取舍：

| dsh 组件 | 核心思想 | 移植结果 |
| --- | --- | --- |
| `core/agent-loop` | "call model, run tools, repeat"：turn → steps → 模型请求 + 工具执行 → 结果写回日志 → 下一步 | ✅ `agent-loop.ts`，单回合步数预算（默认 6）防循环 |
| `core/session` | append-only 会话日志是模型上下文唯一事实源（"model-visible means logged"） | ✅ `session-log.ts`，`derive()` 从日志投影对话转写（内存版，结构保留持久化可能） |
| `core/tools` | 工具 = schema + 受守卫执行；参数校验失败/异常都变成结构化结果，永不抛进 loop | ✅ `tool-registry.ts`（必填/枚举/类型校验 + 异常捕获） |
| `core/system-prompt` | 系统提示词按 order 分段组装（身份/上下文/工具目录/策略/协议） | ✅ `prompt-sections.ts` 六段组装 |
| `llm/llm` adapter seam | 模型适配器可替换 | ✅ `agent-adapter.ts`：基于现有 `callAI` 的 JSON 协议适配器，任何 OpenAI 兼容端点（含 Ollama）可用 |
| memory | 槽位记忆 + 工具写入 | ✅ `update_memory` 工具 + 白名单槽位 |
| Cordis 插件树/profile/bundle | 进程级插件组合 | ❌ 不移植：Obsidian 插件已有 EngineRegistry，进程级插件框架过重 |

未采用 provider 原生 function calling：适配器把会话历史折叠进 user 消息、要求模型输出 JSON 协议（`reply` / `chips` / `tool`），兼容所有 OpenAI 兼容端点；解析器容忍代码围栏、前后杂文本，非 JSON 纯文本整体按 reply 兜底。

### 8.3 字体格式调研与载入模块

| 格式 | 特性 | 结论 |
| --- | --- | --- |
| TTF / OTF | 原始轮廓格式，兼容性最好，体积最大 | 本地载入无障碍 |
| WOFF | 第一代压缩，体积减 30–50% | 可用 |
| WOFF2 | Brotli 压缩，比 WOFF 再省 20–30%，**Electron/Chromium 完整支持** | **推荐** |
| 中文注意 | 单文件 5–20MB 属正常；分发建议 fonttools（pyftsubset）子集化后再转 WOFF2 | 本地全量载入即可 |

载入方法：CSS `@font-face` 适合静态打包；运行时动态载入用 **FontFace API**——`vault.readBinary` 取 ArrayBuffer → `new FontFace(family, buffer)` → `load()` → `document.fonts.add()`，任意元素 `font-family: "<family>"` 即生效；卸载 `document.fonts.delete()`。

实现（`services/font-manager.ts` + `ui/font-manager-modal.ts`）：

- 字体文件放 vault「`元文件/字体/`」目录（支持 ttf/otf/woff/woff2），随同步保留、用户可直接管理文件；
- 插件启动按 `settings.customFonts` 清单自动恢复注册；弹窗「📥 扫描并载入」增量注册新文件；
- 「🔤 字体管理」弹窗：family 列表（附带该字体渲染的预览文字 + 格式/体积）、移除（只注销不改文件）、说明文案；
- 系统字体无法在浏览器枚举：编辑器字体下拉提供（a）Obsidian 主题变量（正文/界面/等宽）、（b）常见中文系统字体预设栈（微软雅黑/苹方/宋体/楷体/黑体/仿宋/思源黑宋）、（c）自定义载入字体（★ 前缀）三类来源。

## 九、吸收 dsh harness 与视觉层级优化（2026-10-28 第四轮）

### 9.1 创作计划（吸收 dsh `plan/plan-mode`）

dsh 的做法：`/plan` 进入计划模式 → 模型把计划写成 Markdown → `exit_plan_mode` 交给用户审阅（Approve / Keep planning）。

移植到小说创作场景：计划不是阻塞式审阅，而是**贯穿多步任务的实时进度条**。

- 新增工具 `update_plan(steps)`：`[{step, status: pending|in_progress|done}]`，最多 8 步；
- 计划状态由 `AgentHarnessEngine` 持有，`getPlan()` 供 UI 读取；
- 系统提示词新增 `【创作计划】` 段（order 15，紧随身份段），让模型每步都能看到当前进度并主动更新；

### 9.2 会话压缩（吸收 dsh `compaction/`）

dsh 的做法：token 压力触发 → 把一段历史**范围替换**为一个摘要节点；关键约束是切割点必须**工具配对平衡**（每个 tool_call 的 tool_result 必须在同一侧），见 `tool-pairing.ts` 的 balance 折叠。

移植实现（`session-log.ts#compactToSummary`）：

1. 扫描事件流，计算每个下标处的未闭合 tool_call 数（`balanceAt`）；
2. 从尾部数 `keepTurns` 条派生轮次确定保留区起点；
3. 从该点向前找最近的 `balanceAt[i] === 0` 作为安全切割点；
4. 把 `[0, cut)` 替换为一个 `user_message` 摘要节点，`system_message` 原样保留。

摘要由一次**独立 AI 调用**生成（`system` 含「会话压缩器」，与回合回复解耦，失败静默跳过不影响回合）。工作台启用配置：`thresholdTurns: 30, keepTurns: 12`。

## 十二、API 格式下拉与从 URL 获取模型（2026-10-29）

**用户需求**：设置页的 API 端点参照参考界面改成「Base URL + 格式下拉」，并从 dsh 提取「从 URL 拿模型」的能力，不再手动输模型名。

### 12.1 前置判断：先补协议，再做下拉

梳理现有调用链后确认：运行时只有两条协议——OpenAI Chat Completions 与 Ollama `/api/generate`。如果只加一个 Anthropic 下拉，选中后请求仍按 `messages` + Bearer 发出，服务端回 400/401，用户会以为「插件不支持这个中转站」。因此先做协议适配层，UI 才有意义。

### 12.2 协议适配层（`shared/api-format.ts`）

| 维度 | openai-chat | anthropic-messages | openai-responses |
| --- | --- | --- | --- |
| 请求路径 | `{root}/v1/chat/completions` | `{root}/v1/messages` | `{root}/v1/responses` |
| 系统提示 | `messages[role=system]` | 顶层 `system` 字符串 | `instructions` |
| 用户输入 | `messages[role=user]` | `messages[role=user]` | `input` |
| 输出上限 | `max_tokens` | `max_tokens` | `max_output_tokens` |
| 鉴权 | `Authorization: Bearer` | `x-api-key` + `anthropic-version: 2023-06-01` | `Authorization: Bearer` |
| 非流式正文 | `choices[0].message.content` | `content[type=text].text` 拼接 | `output_text` 或 `output[].content[]` |
| 截断信号 | `finish_reason=length` | `stop_reason=max_tokens` | `incomplete_details.reason=max_output_tokens` |
| SSE 增量 | `choices[0].delta.content` | `content_block_delta.text_delta` | `response.output_text.delta` |
| 结束标记 | `data: [DONE]` | `message_stop` | `response.completed` / `response.incomplete` |

关键细节：

- `resolveApiRoot` 剥掉已写全的 `/chat/completions`、`/responses`、`/messages` 与结尾 `/v1`，所以**历史配置里存着完整 URL 的老用户不需要迁移**（有单测锁死这条）。
- Anthropic 的 `thinking.budget_tokens` 必须小于 `max_tokens`，否则 400；实现里做了夹取，装不下就干脆不发。
- 适配层是纯函数，无 Obsidian 依赖，35 条单测直接覆盖四段（URL / 请求体 / 非流式解析 / SSE 帧）。

`AIApiClient` 四条调用路径（`callAI`、`callAIStream`、`callAIAsyncIterator`、`nativeStreamIterator`）统一改用 `resolveRequestEndpoint` + `buildAuthHeaders` + `parseSseFrame`；Ollama 原生端点仍优先改写（要 `num_ctx`），不受影响。连通性测试也接同一套，避免「格式选对了但测试仍按 OpenAI 发」。

### 12.3 从 URL 获取模型（`services/model-discovery.ts`）

对照 dsh `llm-pi-ai/src/discovery.ts` 移植，保留了三条设计原则：

1. **只给候选，不替用户写配置**——请求结果进勾选弹窗，用户确认才落盘；
2. **响应有体量上限**——超过 2MB 直接拒绝并说明，防止任意 URL 把内存打满；
3. **失败要说清原因**——401/403 提示查密钥、404 提示该端点可能不提供列表、非 JSON、超时、空列表各有独立文案，而不是返回空数组让用户以为端点没模型。

### 12.4 踩到的坑：CSS 类名撞车

### 14.1 规则版本「重新检查」重复生成模块

**根因**：`renderRulesSection()` 每次执行都 `this.tabContent.createEl('section')` **追加**新节点，而「🔄 重新检查」按钮的回调正是 `this.renderRulesSection()`——每点一次就多出一整块完整模块（截图里能看到两块一模一样的规则卡片）。

**修法**：拆成两个方法：

```ts
private async renderRulesSection() {
    const section = this.tabContent.createEl('section');  // 只建一次根容器
    await this.mountRulesSection(section);
}
private async mountRulesSection(section) {
    section.empty();   // 幂等：重绘前先清空
    ...渲染内容...
    refreshBtn.onclick = () => this.mountRulesSection(section);  // 只重绘本容器
}
```

**全仓排查**：设置页共 18 个 `render*Section`，逐一检查「是否自调用」「是否直接往 tabContent 追加」。结论是只有 rules 一处自调用；其余都通过 `renderActiveTab()`（它先 `tabContent.empty()`）。另加两条静态测试锁死：
- 事件回调里不得出现 `this.render*Section(...)`；
- 每个 `render*Section` 都必须从 `tabContent` 起自己的 `<section>`。

**真实 Obsidian 验证**：连点 3 次「重新检查」，`.nw-settings-tab-content > section` 数量恒为 1（`RULES_SECTION_COUNT {"before":1,"after":1}`）。

### 14.2 颜色配置 5 层 → 3 层

旧模型的实际层级：

| 层 | 配置项 | 问题 |
| --- | --- | --- |
| 1 | 底色 `appBg` | — |
| 2 | 面板色 `panelBg` | 与底色几乎总是联动，用户不知道该不该改 |
| 3 | 卡片背景色 `cardBg` | 被 `enableCustomCardBg` 开关包住，形成第 4 层条件判断 |
| 4 | 强调色 `accent` | — |
| 5 | 主文字色 `textPrimary` | 实为对比度问题，不该让用户手配 |

CSS 侧还有 `--nw-surface`、`--nw-cover-bg` 两个平行背景 token，与 `--nw-panel-bg` 语义重叠。

**新模型**（`shared/theme-colors.ts`）：

- **L1 基底** `--nw-app-bg`：唯一需要用户决定的背景；
- **L2 卡片** `--nw-card-bg`：留空则按氛围预设 `color-mix` 从基底抬起；
- **L3 强调** `--nw-accent`：hover 按基底明暗自动加深/提亮；
- 面板 = 基底 + 预设步长派生，`--nw-surface` 直接等于面板值；
- 文字色由 `deriveTextColors()` 按基底 WCAG 相对亮度自动选深/浅两套，想覆盖时才展开「覆盖文字色」高级项。

`derivePalette()` 是纯函数，把三层输入 + 主题默认值算成整套变量；`ThemeManager` 不再手写 if 链。E2E 断言：`基底色/卡片色/强调色` 三项存在，`面板色` 与 `启用自定义卡片背景` 已消失，预览色板恰为 3 个。

### 14.3 主题配色方案

新增 `themePresets` 存储与完整管理：

- **保存**：`capturePreset()` 从当前 themeColors 抓取，同名覆盖，上限 20 套，超限淘汰最旧；
- **切换**：`presetToSettings()` 整体替换 themeColors（不 merge），避免旧字段残留导致「切了方案还在用旧色」；
- **导入导出**：JSON 单套/数组皆可，`parsePresetImport()` 丢弃非法颜色、id 冲突换新、非对象跳过；
- 列表显示三色色板 + 主题模式 + 当前使用中标记。

### 14.4 性能：取色不再全量重渲染

旧实现每次 `onChange` 都 `await plugin.saveSettings()`（磁盘写入）+ `rerender()`（整块 DOM 重建）。拖动取色器会连续触发几十次。改为：

```ts
const applyLive = () => { plugin.injectThemeVariables(); scheduleSave(); };  // 防抖 300ms
```

视觉立即生效，落盘合并，不重建 DOM。

另清理两处死代码：`.nw-theme-preview-swatch-panel`（三层模型下不再渲染该色板）与完全重复的 `.nw-awb-quick` 样式块。

## 十六、补盲点与下拉缺陷定位（2026-10-29 收尾）

### 16.1 下拉「字体不全」——先量再改

用户反馈「API 格式下拉显示字体不全」，并问这是单一问题还是所有类型都有。**结论：类级缺陷，三种下拉里两种有问题。**

用真实 Obsidian 探针测量（不靠肉眼）：

| 选择器 | 宽度 | 可用内宽 | 文本宽 | 溢出 | 结论 |
| --- | --- | --- | --- | --- | --- |
| `.nw-api-select` | 340 | 300 | 238 | -62 | 当前宽度不溢出，但**无箭头** |
| `.nw-api-select`（模拟 240px 面板） | 240 | 200 | 238 | **+38** | 窄面板必然截断 |
| `.nw-select`（12 模型预算选择器） | 261 | 237 | 240 | **+3** | 已溢出，且被切在笔画中间 |
| Obsidian 原生 `.dropdown` | 185 | 143 | 143 | 0 | 正常 |

三层根因，层层叠加：

1. **没有箭头**：Obsidian 全局对 `select` 设 `appearance: none`，箭头是 `.dropdown` 类上的 data-URI SVG 背景图。插件的 `.nw-select` / `.nw-api-select` 没有那个类 → 完全没有三角，文字一路顶到右边缘，「看不出这是下拉」。
2. **右侧没留位**：`.nw-select` 是 `padding: 0 12px`，12px 连箭头都放不下；且缺 `text-overflow`，超长选项直接切在字中间。各业务变体（`.novel-writer-fw-chapter-select` 的 `padding: 0 10px`、`.novel-writer-fw-title` 的 `padding: 4px 8px`）在文件更后面，把统一值又覆盖回去。
3. **箭头画了也看不见**：`getComputedStyle` 显示 `background-blend-mode: hard-light`（Obsidian 设的）。灰色箭头与背景色混合后完全不可见——实测右侧 60px 裁图里没有任何像素。**这也是上一版两个渐变三角形混成畸形「↖」的原因**：它们被 hard-light 混出了怪形状。

### 16.2 修法与验证

- 两个下拉类各自内联一个 **URL 编码的 SVG chevron**（10×6，stroke #808080），显式 `background-blend-mode: normal`；

## 十七、任务参数调节引擎与设置行排版修复（2026-10-29）

### 17.1 设置行被压成竖排单字

**现象**：同人考据来源的「最大来源数 / 单源摘录长度」渲染成一列竖排单字（每个汉字占一行）。

**根因**：Obsidian 的 `.setting-item` 是 flex 行，`.setting-item-info` 带 `min-width: 0`。右侧两个数字输入框较宽时，信息列被压到极窄；中文可在任意字符处断行，于是逐字换行。这不是本项目特有写法的问题，而是「长标签 + 宽控件」这一组合的通用陷阱。

**修复**：
1. 把合并标签拆成两条独立设置（语义也更清楚）；
2. 加防御性 CSS——`.setting-item-info` 给 200px 可读下限、整行允许 wrap、控件放不下时落到下一行。

**踩到的坑**：第一版守卫只写了 `.nw-scope`，而设置页容器根本没有这个类（只有各弹窗才有），于是守卫完全没生效。E2E 的「无竖排单字」断言立刻抓到另外两处既有问题：
- 「Flash 模型（大纲/分析/规划）」被压到 70px
- 「Pro 模型（正文/角色/实体）」被压到 25px

把选择器补上 `.nw-settings-tab-content` 后归零。这条断言（`SETTINGS_LAYOUT.squeezed === []`）现在作为常驻回归。

### 17.2 任务级参数：30 个控件 → 1 个档位

旧 UI 给 6 个任务各一张卡片，每张 5 个控件（模型 / 最大输入 / 最大输出 / 思考等级 / 思考预算），共 30 个，用户还要自己保证它们彼此一致（例如输出不能超模型能力）。这既难维护也难解释。

改为引擎驱动（`shared/task-budget-engine.ts`）：

| 概念 | 说明 |
| --- | --- |
| 预算档位 | `lean / balanced / generous / extreme` 四档，唯一需要用户选的输入/输出旋钮 |
| 任务类别 | `planning / writing / analysis`，由引擎固定映射，不暴露给用户 |
| 分发 | 档位系数 × 模型能力 → 输入预算 / 输出上限 / 思考预算 |

关键约束是**默认档与旧行为逐值一致**：`balanced` 三类系数全为 1，输入仍按 `floor(context - output × 1.15)` 计算（连取整顺序都比对过，避免差 1 个 token）。这样升级不会静默改变生成质量或成本。

保留的历史分支：旧实现里「只有 `thinkingMode` + `thinkingBudget`、无显式等级/强度」时，预算是**直取不缩放、也不自动预留**。引擎接入后这条路径原样保留，否则「设了 300」会悄悄变成「按强度自动分配」。

兼容：`taskBudgets` 里的手工覆盖仍优先于引擎；设置页会统计并提示「检测到 N 个旧覆盖」，提供一键清除。

## 十八、模型切换器溢出修复（2026-10-29）

### 18.1 现象与量测

知识库左栏顶部的「🔌 供应商 · 模型」胶囊按钮右半截压到相邻栏目，图标看着像被切掉。

| 元素 | 宽度 | 右边缘 |
| --- | --- | --- |

### 18.2 根因（三个叠加）

3. label 作为 flex 子项默认 `min-width: auto`，会撑住父元素，使 `text-overflow: ellipsis` 也失效。

```css
.nw-model-switch {

    flex: 0 1 auto;               /* 允许在行内布局里收缩 */
}
.nw-model-switch-label {
    min-width: 0;                 /* 让省略号真正生效 */
}
```

### 18.4 验证

- 指纹库侧栏（同一组件、300px 侧栏）：`FP_SWITCHER {"sidebarW":300,"buttonW":280,"overflowRight":-20}`

**测试本身的坑**：页面上可能同时存在多个 `.nw-model-switch`（Agent 工作台、协同写作各挂一个），全局 `querySelector` 会命中隐藏的那个、宽度为 0，断言就成了空过。必须限定 `.nw-kb-left-sidebar .nw-model-switch`，并先 `poll` 到宽度 > 40 再断言。

## 二十、Bug 巡查：API Key 失效根因与联动板块（2026-10-29）

用户报告「API Key 配置经常每次更新后失效」，确认是 Bug，要求按板块巡查、联动板块同步检查。

### 20.1 取证：真实数据先说

只看代码会陷入猜测，先看 `data.json` 里密钥字段的**形状**（不打印内容）：

```text
apiKey                : plaintext(sk-) len=35
providerKeys.catcat   : aes256v2 len=150
providerKeys.deepseek : plaintext(sk-) len=35   ← 与 apiKey 同值
providerKeys.volc     : aes256v2 len=270
providerKeys.custom-1 : plaintext(other) len=51
providerKeys.custom-2 : aes256v2 len=250
providerKeys.custom-3 : aes256v2 len=282
```

**同一次保存不可能产生「部分密文 + 部分明文」**。这种混合状态本身就说明有两条不一致的写入路径。

### 20.2 根因：每次重启都在悄悄「重设口令」

加密格式是 `aes256v2:<iterations>:<salt>:<iv>:<ct>`，口令 + PBKDF2，盐随密文存——设计上跨版本稳定。问题在口令获取：

```ts
// 修复前
private async ensurePassword(isNew: boolean) {
    const ask = isNew ? this.callbacks.requestNewPassword : this.callbacks.requestPassword;
    ...
}
```

`encrypt()` 调用 `ensurePassword(true)`，于是**无论磁盘上有多少密文，都走 `requestNewPassword` → `PasswordModal.setup`（「设定新口令」，两次输入）**。而会话口令只存内存：

1. 重启/更新 → 会话口令为空；
2. 保存任意密钥 → 弹「设定新口令」；
3. 用户再设一次（哪怕是同一个口令，也很容易打错或换一个）；
4. 新口令设为会话口令 → 旧密文全部解不开。

每重启一次就可能再坏一批。这与「每次更新后失效」的现象完全吻合。

### 20.3 修复

**（1）口令一致性守卫**（`core/crypto-service.ts`）

新增回调 `findExistingCiphertext()`，由 `SettingsService` 从「磁盘原始值快照」提供。`ensurePassword` 改为：

- 磁盘上已有密文 → **即使调用方请求「新口令」，也只能问「已有口令」**；
- 候选口令必须能解开一条既有密文（GCM 校验）才被接受；
- 错两次 → 返回 null，不设会话口令，也不会用错口令去加密。

`verifyPasswordAgainst` 刻意绕过 `_derivedKeys` 缓存：错误口令派生出的 key 若被缓存，后续正确口令会命中脏缓存。

**（2）不把密文降级为明文**（`core/settings-service.ts`）

原 `encryptIfPlain` 在「无会话口令」时直接写回内存值——而此时内存值已被解密成明文。改为 `resolveSecret(field, value)`：

| 情况 | 落盘值 |
| --- | --- |
| 已是密文 | 原样保留 |
| 有会话口令 | `encryptStrict` 加密 |
| 无口令，但磁盘原本是密文 | `encryptStrict`（问已有口令）；取消则**保留旧密文**，记 warn |
| 从未用过口令 | 明文（保留旧行为） |

配 `rawSecrets` 快照（`loadSettings` 时记录解密前的磁盘值）作为判据。

**（3）密钥输入框不再泄露密文**（`shared/secret-display.ts`）

未解锁时内存值是密文，三处 UI（设置页 / 统一提供商弹窗 / 迷你设置）原先把密文塞进输入框：用户看到乱码，误编辑还会把密文当新密钥保存。现在密文一律显示为空 + 「已加密 · 输入口令解锁后可修改」，并且**留空失焦不写回**，避免把密文清掉。

**（4）恢复入口**

设置页新增「密钥加密」行：显示锁定条目数，提供「输入口令解锁」与「重置口令」。重置会重加密所有可读明文，**解不开的旧密文清空并列名**，让用户知道哪些供应商要重填——而不是让它们停在「看起来配好了但实际无效」的状态。

## 二十二、写作指纹库审计：持久化、作用域与向量清理（2026-10-30）

用户指令：「接下来修复写作指纹库板块代码内容。查看现有代码进行优化」。本轮按数据链路（磁盘 → 内存 → UI → 回写）逐段审计，共修 16 处，其中 4 处属于会**静默损坏用户数据**的缺陷。

### 22.1 P0：融合指纹的特征一直是空的

`StyleFingerprintLibrary.extractV1FeaturesFromV2()` 的反向映射解构写反了：

```ts
const v2ToV1Map = { rhythm: 'sentenceRhythm', /* ... */ };
for (const [v1Key, v2Key] of Object.entries(v2ToV1Map)) {   // ← 顺序反了
    const dim = features[v2Key];   // features.sentenceRhythm → undefined
```

于是「V2 → V1 投影」恒返回 `{}`。`saveBlendedFingerprint()` 正是用它生成落盘特征，所以**任何通过「🎨 融合预览」保存的指纹都只有统计数字，七维风格特征全空**，注入到正文里等于没融合。`toPersistedFingerprint()`（本轮新增）也依赖它做「V2 是否过期」判定，写反后判定恒为「一致」，会把陈旧 V2 一直写回磁盘。

修法：`[v2Key, v1Key]`，并写了一条「把顺序改回写反的版本必然失败」的回归用例（`fingerprint-library-persist-guard.test.ts` 的「V1 特征被重新提取后不再回写陈旧 V2」）。已实测：临时把解构改回去，该用例立即红。

### 23.1 P0：索引解析失败 = 整库清零

`KnowledgeBaseManager.loadIndex()` 依赖 `parseFrontmatter()`，而后者在 `JSON.parse` 失败时返回 `{}`：

```ts
private parseFrontmatter(content: string): Record<string, unknown> {
    const match = content.match(/^---\n([\s\S]*?)\n---/);
    if (!match) return {};
    try { return JSON.parse(match[1]); } catch { return {}; }   // ← 吞掉解析错误
}
```

`loadIndex` 于是看到「没有 books 数组」，走 `this.books = new Map()` 分支——注意它**不是** catch 分支，所以已有的 `rebuildIndexFromBooks()`（把坏索引改名 `.bak` 并从书籍目录恢复）完全不会触发。下一次 `saveIndex()`（任何一次 addBook/改状态/重建）就把「0 本书」写回磁盘。

同一段代码还有第二个触发点：正则只认 `\n---`。索引是用户可见的 `.md`，在 Windows 上被外部编辑器保存一次就变成 `\r\n`，于是匹配失败 → 同样清零。

修法两处：
1. `loadIndex` 在「索引存在但没有 `books` 数组」时主动 `throw`，与读取/解析失败共用同一条重建路径；
2. `parseFrontmatter` 先 `replace(/\r\n/g, '\n')` 再匹配。

`rebuildIndexFromBooks` 本身早已写好（改名留档 + 按目录扫描 + 校验书名），缺的只是「别把解析失败当成空库」这一步。

## 二十六、Agent 创作工作台审计：项目越界、任意命令与回合失控（2026-10-30）

### 26.1 P0：项目名 `..` 能删掉整个 Vault

`newProjectPath()` 只剥斜杠：

```ts
const safeName = String(name || '').replace(/[\/]+/g, '');
return `${MODE_LIBRARY_ROOTS[mode]}/${safeName}`;
```

`create_long_project` 又只校验非空。项目名来自模型输出（可被提示注入影响），传 `".."` 时目标路径归一化为 Vault 根，`"."` 为模式库根；再叠加端口里硬编码的 `confirmOverwrite: async () => true`，`createLongNovelProject` 会先递归删除同名目录再重建 —— **整个项目库甚至整个 Vault 被清空**。

修法两层：
1. `newProjectPath` 拒绝空名 / `.` / `..` / 纯点号，抛「非法项目名」；
2. Agent 端口 `confirmOverwrite` 恒 `false`：同名创建返回失败，让模型换名或先问用户。**Agent 永远不覆盖已有项目**。

### 26.2 P0：`run_command` 可执行任意 Obsidian 命令

工具只要求 `commandId` 非空，`plugin.executeCommand` 在 registry 未命中时回退到 `app.commands.executeCommandById`，于是 `app:delete-file`、第三方插件命令都能被 Agent 无确认执行，且 fire-and-forget 的失败被忽略、工具仍回报成功。

修法：工具层只接受 `novel-writer-*`；端口层要求 `plugin.registry.has(commandId)`，未命中直接失败。

### 26.3 P0：项目参数越界读写

`resolveProject` 对未命中的显式 `project` **原样返回**，`open_story_settings` 直接把它交给弹窗，保存时 `adapter.write(`${project}/.project`)`、`mkdir(`${project}/00-系统模板`)` —— 模型传 `../..` 即可越界写入。`list_chapters`/`get_project_status` 同样会把任意路径当项目读。

修法：显式参数必须是 `ctx.projects` 里真实存在的条目（精确或后缀匹配）；记忆里的 `pickedProject` 只接受「库/项目」形状且不含 `.`/`..`/隐藏段；解析为空时所有相关工具返回「项目不存在或未指定」。

### 26.4 P0：关闭工作台不停止回合

`AgentHarnessEngine` 支持 `options.signal`，但唯一构造点没传；`onClose` 只把引擎置 null。用户关闭后模型调用与工具继续执行（创建项目、批量生成、导出），完成后还往已脱离的 DOM 写消息。

修法：每个会话一个 `AbortController` 传给引擎；`onClose`/`restart` 时 abort；loop 在每步开始、每次工具执行前检查 `signal.aborted`。

### 26.5 P0：同一工具在一回合内被重复放大

loop 无条件执行模型给出的工具，`maxSteps` 默认 6 → 同一个 `create_*`/`run_command` 最多执行 6 次。

修法：本回合内「工具名 + 参数」去重，重复调用不再执行，返回「重复调用已被阻止」让模型改用上一次结果。

## 二十七、深度吸收 dsh harness：把 dsh 的机制映射到插件（2026-10-30）

用户指令：「吸收下方路径中的 dsh 的 harness 工程，吸收到插件里面去。将插件完整优化完全。」路径 `D:\小说工坊\小说工坊\deepseek-harness\deepseek-harness-master`。

dsh 是一个 Cordis 驱动的「everything-is-a-plugin」工程（50+ 包：核心 loop、session、compaction、llm、guard、interaction、subagent、skill、jobs…），不可能整体搬进 Obsidian 插件。本轮按「机制吸收、实现自研」：保留插件既有的内存日志 + JSON 协议 + 注入端口架构，把 dsh 里**与小说创作 Agent 直接相关、且能落地验证**的五类机制吸收进来。

### 27.1 工具结果确定性裁剪（对应 `compaction/compaction-tool-result-pruner`）

dsh 的做法是不调模型、把超预算工具结果的「头 + 尾」保留、中段替换为标记，并且**不改写原事件**，只在表面（surface）投影时生效，因此可重放。

插件现状：`list_chapters`、`list_commands`、`run_command` 的结果可达数 KB，`derive()` 每步都整段发给模型；会话压缩只在 30 轮时触发，中间这些超大结果一直占着上下文。

实现 `engine/agent/harness/tool-result-pruner.ts`：

- 预算 6000 字符（头 1200 / 尾 1200 可配），按 Unicode 码点切片，避免切开 emoji 的代理对；
- `PRUNE_MARKER` 明确告诉模型「中间被裁掉，需要全文请重新查询」；
- 只在 `derive()` 投影时裁剪，`snapshot()` 仍是原文（可审计/可重放）；
- `pruneStats` 进入遥测，工作台右栏新增「省字符 / 压缩」两格。

### 27.2 工具超时（对应 `guard/timeout-policy`）

dsh 在 `tools/execute` 上挂一个 deadline 包装器：工具声明 `timeoutMs`，超时后工具自己感知到 abort，包装器再把结果替换为结构化 `TOOL_TIMEOUT`。

插件实现：`HarnessTool` 增加 `timeoutMs`，`HarnessToolRegistry.execute` 派生 AbortController（与上游 signal 联动），超时先 abort 再返回 `{ok:false, content:'…超时（Nms）…', data:{errorCode:'TOOL_TIMEOUT'}}`；工具的 Promise 不被丢弃（不会产生未处理 rejection）。预算：`create_*` 20s、`list_*` 10–15s、`run_command` 30s。

### 27.3 重复调用提醒（对应 `guard/repeat-tool-reminder`）

dsh 是 **advisory**：连续重复到达阈值（默认 3/5/8）时注入一条提醒，而不是否决调用。插件上一轮实现的是「同名同参第二次就硬拦截」，对只读工具过严（例如改完文件后再查一次章节列表）。

本轮改为按副作用分级：

- 新增 `sideEffect: 'none' | 'write' | 'dangerous'`；
- `none`（只读）：允许重复执行，连续 3/5/8 次时注入 `context_message` 提醒（进入转写、按 user 角色呈现）；
- `write` / `dangerous`：第二次重复直接拦截（创建/修改类副作用不可逆）；
- 参数用「深度键排序后 stringify」规范化（dsh `canonicalize`），只有属性顺序不同视为同一次调用；
- 工具目录把副作用写进系统提示词，模型提前知道哪些调用会改数据。

### 27.4 回合内补充与压力压缩（对应 `core/agent-loop` inbox、`compaction/compaction-basic`）

- **steering**：`AgentHarnessEngine.steer(text)` 在回合进行中把用户补充放进收件箱，loop 每步调模型前写入日志（带「用户在你执行过程中补充」前缀）；工作台在 busy 时不再直接丢弃输入，而是提示「已插入当前回合」。回合结束仍未被消费的消息保留为普通用户消息，不丢失。
- **压力触发**：会话压缩的触发条件从「轮次 ≥ 30」扩展为「轮次 ≥ 30 **或** 投影字符 ≥ 32000」（`thresholdChars` 可配）。只靠轮次时，几段超长工具结果会一直撑满上下文。

### 27.5 危险命令用户确认（对应 `interaction/user-approval`）

dsh 把审批作为独立交互层。插件此前 `run_command` 只限制在 `novel-writer-*`，但批量生成/结算/导出仍可被模型直接触发。

## 二十九、成稿导出格式扩展：TXT / EPUB / DOCX（2026-10-27）

### 29.1 目标与取舍

原有导出只有 Markdown / 纯文本 / HTML（HTML 靠浏览器打印成 PDF）。本轮补齐「常见小说格式」：

- **EPUB 3**：电子书事实标准，手机阅读器/微信读书可直接导入，Kindle 侧可用官方转换；
- **DOCX**：投稿平台与编辑改稿最常用；
- **TXT**：保留并补 BOM 选项，仍是网文平台最稳的提交格式。

不做的格式与原因：MOBI/AZW3 需要 Kindle 官方工具链，插件内无法可靠生成；PDF 需要主进程 `printToPDF`（插件拿不到），继续用 HTML 打印路径；RTF/ODT 对小说投稿没有额外收益。

### 29.2 实现

- **ZIP 打包（`engine/export/zip-writer.ts`）**：EPUB/DOCX 本质都是 ZIP，插件不允许运行时依赖，因此实现 store（method=0）+ CRC32 + EOCD 的最小写入器。纯 ASCII 路径不置 UTF-8 标志，保证 EPUB 的 `mimetype` 条目「首个 + 不压缩 + 无 extra field」，同时中文文件名仍可读。写入可传入固定日期，便于测试与可复现导出。
- **EPUB（`engine/export/epub-builder.ts`）**：OCF 目录 `mimetype` → `META-INF/container.xml` → `OEBPS/{content.opf,nav.xhtml,toc.ncx,style.css}` → `OEBPS/text/chapter-000N.xhtml`。`content.opf` 写 `dc:title/creator/language`、`dcterms:modified`、manifest 与 spine；`toc.ncx` 保留 EPUB2 兼容。每章独立 XHTML，卷标题只在卷首章出现；正文按行拆段（项目正文约定「一个自然段一行」），剔除 frontmatter 与模板 H1，XML 控制字符与 `& < > " '` 全部转义。
- **DOCX（`engine/export/docx-builder.ts`）**：`[Content_Types].xml`、`_rels/.rels`、`word/document.xml`、`word/styles.xml`、`word/_rels/document.xml.rels`、`docProps/{core,app}.xml`。`styles.xml` 定义 Title/Heading1/Heading2/BodyText（宋体、12pt、1.5 倍行距、首行缩进 200 字符单位），每章之间插入分页符；`core.xml` 写标题、作者与创建/修改时间。
- **统计口径统一**：`manuscript-compiler.ts` 抽出 `summarizeManuscriptChapters`，Markdown/TXT/HTML/EPUB/DOCX 的章数、卷数、字数、空章数全部同源，避免「导出提示 10 万字、EPUB 里少一章」。
- **二进制落盘（`shared/export-file.ts`）**：新增 `exportBinaryFile`，桌面走 Blob 下载，移动端/`preferVault` 走 `vault.createBinary` / `modifyBinary`；文件名净化与文本导出一致。
- **导出入口修复**：`ExportManuscriptModal` 之前会把「调用方传入但不在 listProjects 结果里的项目」替换成列表第一个，短篇/剧本从创作流程点「导出」时会导出错项目。现在缺失时保留调用方项目并补进下拉，空列表且无项目才提示。格式下拉新增 EPUB/DOCX，作者与 BOM 选项按格式显隐。

### 28.8 回归修复：写一章被判「结算完成」（2026-10-27）

**现象**：用户只写了 1 章（项目还有后续章节未写），项目页流程摘要显示 40%，阶段圆点为「初始化 ✓ / 章节写作 ○ / 结算 ✓」。总进度正好是长篇权重 `0.25 + 0.15 = 0.40`，说明结算阶段被判成 done。

**根因**：`shared/creation-flow.ts` 的 settlement 阶段用「已结算 / 已写」算完成度：

```ts
const done = written > 0 && settled >= written;
ratio = written > 0 ? ratioOf(settled, written) : 0;
```

单章写完并结算后 `written=1, settled=1`，比值 1/1 = 100%，与「全书是否结算完」无关。章节写作阶段（1/N）还是 active，两个阶段互相矛盾。

**修复**：结算阶段改为按全书规划章数计算：

```ts
const done = total > 0 && settled >= total;
ratio = ratioOf(settled, total);
progressText = `${settled}/${total} 章已结算${written > settled ? `（已写 ${written}）` : ''}`;
```

- 1/10 章已结算 → 结算阶段 active，比例 0.1，总进度 0.25 + 0.05 + 0.015 = 0.32（不再是 0.40）；
- 只有 `settled >= total` 才 done；如果只建了部分骨架，`total` 仍是「已创建的可写章节数」，不会把不存在的章节算成未结算；
- 项目页摘要、流程页、`formatCreationFlowSummary` 共用同一快照，自动同步。

**附带修复**：流程摘要圆点默认用 `--nw-bg-muted`，在橙色主题下与卡片背景同色，未完成阶段完全看不见（用户截图里只数到 3 个点）。给 `.nw-flow-dot` 加 1px `--nw-border` 描边，done 态描边与填充同色，active 态保持 2px 强调环。

**验证**：新增回归用例「只写并结算第 1 章（全书 10 章）不能被判成结算完成」，断言 state=active、ratio=0.1、progressText=`1/10 章已结算`、overall=0.32、nextStage=chapters；全量 **433 文件 5069 用例**、preflight、build、check:release、真实 Obsidian E2E **20 passed** 全绿。CSS 基线因描边字节变化显式更新。
