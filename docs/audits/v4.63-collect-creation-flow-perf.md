# 创作流程采集全库遍历审计（第 57 轮）

> 审计日期：2026-11-07 · 基线 v4.63.0（`5bba29e`）· 类型：audit-only
> 范围：`collectCreationFlowState` 的全库遍历次数、触发点与最小改动方案。
> 本轮**不修改源码**；方案由 ZCode 评审后决定是否实施。

## 0. 结论

1. 「工作台阶段面板每次刷新都重新采集、无缓存复用」**属实**。
2. 「单次采集固定 3 次全库遍历」**不完全准确**：长篇为 3 次；短篇/剧本在新结构下为 2 次（`listModeUnits` 命中 own 后提前返回，不再跑 legacy），只有旧结构回退时才为 3 次。
3. 比 `PERFORMANCE.md` 记录更值得立项的是**重复采集**：`agent-port.getProjectStatus` 先自行统计章节/单元，再调用 `collectCreationFlowState` 重算同一批事实。工作台一次阶段刷新实际为长篇 5 次、短篇/剧本 3 次（旧结构 5 次）。
4. 两个最小改动（导出产物判断改目录内计数、own+legacy 合并为一次 `getFiles`）都属低风险、语义等价；但它们只解决「单次采集」，`agent-port` 的重复统计需要第二阶段方案。

## 1. 事实核对

### 1.1 单次 `collectCreationFlowState` 的全库遍历

| 模式 / 分支 | 遍历来源 | 次数 |
|---|---|---|
| 长篇 | `hasExportArtifact()` 的 `vault.getFiles()`；`getChaptersForProject()` 的 `getFiles()` + `getAllLoadedFiles()` | **3** |
| 短篇/剧本（新结构，own 命中） | `hasExportArtifact()` 1 次；`listModeUnits()` own 1 次（`own.length > 0` 即返回） | **2** |
| 短篇/剧本（旧结构回退） | `hasExportArtifact()` 1 次；`listModeUnits()` own 1 次 + legacy 1 次 | **3** |

- [project-utils.ts](file:///d:/小说工坊/小说工坊/.obsidian/plugins/novel-writer-ai/ui/project-utils.ts#L277-L284)：`getChaptersForProject` = `getFiles()` + `getAllLoadedFiles()`，两次全库遍历。

`readDocFacts`、`readProjectMeta`、`readPreResearchData` 只做 `adapter.exists/read`，属定点 I/O，不计入全库遍历。

## 3. 成本量化

用仓库内基准 `npm run bench:hotpath`（模拟 vault：200 章 × 9 步骤 + 80 实体 + 8,000 篇无关笔记 = **10,080 个文件**，300 次取均值，Node 合成树）实测「全库 flatten + 前缀过滤」单次：

| 场景 | 单次全库遍历 + 过滤 |
|---|---|
| 本卷正文目录定位 | 0.490 ms |
| 项目角色目录 | 0.464 ms |
| 章节递归扫描 | 0.268 ms |
| 正文全量扫描 | 0.208 ms |
| 单章目录查文件 | 0.516 ms |

取 0.25–0.50 ms/次作为数量级（时间只作参考，访问量才是确定性指标：每次 10,080 个文件）：

- 长篇单次采集 3 次 ≈ **0.8–1.5 ms**；一次阶段刷新合计 5 次 ≈ **1.3–2.5 ms**。
- 短篇/剧本新结构单次采集 2 次 ≈ **0.5–1.0 ms**；阶段刷新 3 次 ≈ **0.8–1.5 ms**。
- 旧结构回退与长篇同量级。
- 开销随 vault 文件总数**线性增长**；对 1 万+ 笔记的仓库，上述数字随规模继续放大。
- 本路径不在 `check-hotpath-scans` 的 `HOT_FILES` 内，门禁不会报警（[PERFORMANCE.md §2](file:///d:/小说工坊/小说工坊/.obsidian/plugins/novel-writer-ai/docs/PERFORMANCE.md#L24-L34)）。
- 上述为 Node 合成树下限；Obsidian 的 `getFiles()` 还要构造整库数组（`Object.values`），真机成本更高。本轮无插件内埋点数据，**不编造真机毫秒数**。

## 4. 最小改动方案（未实施）

### A1. `hasExportArtifact`：目录内文件计数，替代全库 `getFiles`

不能改用 `folderExists`：短篇/剧本项目创建时已预建 `05-导出`/`06-导出`（[mode-content.ts](file:///d:/小说工坊/小说工坊/.obsidian/plugins/novel-writer-ai/shared/mode-content.ts#L306-L331)），目录恒存在，`folderExists` 会恒真。应统计目录内文件：

```ts
function hasExportArtifact(app: App, project: string): boolean {
    if (readExportFlag(project)) return true;
    const baseName = project.split('/').pop() || project;
    const exportDirs = [`${project}/05-导出`, `${project}/06-导出`];
    for (const dir of exportDirs) {
        if (listFolderFiles(app.vault, dir, { recursive: true, extensions: [] }).length > 0) return true;
    }
    const fallback = listFolderFiles(app.vault, EXPORT_FALLBACK_DIR, { recursive: true, extensions: [] });
    return fallback.some(file => file.name.includes(baseName));
}
```

- 复用 `shared/vault-tree.ts` 的 `listFolderFiles`（`getAbstractFileByPath` O(1) 定位 + `children` 局部遍历），函数保持**同步**，调用点无需改。
- 语义变化：原本只看直属文件，改为递归计数；导出目录写入的是直属文件，实际等价，且更贴近「有导出产物」的本意。
- 预期：每次采集省 **1 次全库遍历**。

### A2. `listModeUnits`：own + legacy 合并为一次 `getFiles`

```ts
export function listModeUnits(app: App, project: string, mode: CreationMode): ModeUnitInfo[] {
    if (mode === 'long') return [];
    const dir = modeBodyDir(project, mode);
    const pattern = mode === 'short' ? /第\d{1,3}节\.md$/ : /第\d{1,3}集\.md$/;
    const legacyPrefix = `${project}/03-大纲与章节/正文/`;
    const files = app.vault.getFiles();  // 只扫一次，own 与 legacy 共用
    const own = files
        .filter(file => file.path.startsWith(`${dir}/`) && pattern.test(file.name))
        .map(file => unitInfo(app, file, mode, false))
        .filter((item): item is ModeUnitInfo => !!item);
    if (own.length > 0) return own.sort((a, b) => a.number - b.number);
    return files
        .filter(file => file.path.startsWith(legacyPrefix) && /第\d+章_正文\.md$/.test(file.name))
        .map(/* 保持现有 legacy 映射 */) as ModeUnitInfo[];
}
```

- 预期：旧结构回退分支 **2→1**；新结构分支不变（仍 1 次）。
- 注意保留现有 legacy 的 `number/title/status` 映射与排序，避免口径漂移。

## 5. 第二阶段方案（需 ZCode 评审，收益更大）

`agent-port.getProjectStatus` 的重复统计：

- 它先用 `getChaptersForProject` / `listModeUnits` 统计 `progress`，随后 `collectCreationFlowState` 又对同一批章节/单元重扫一遍。
- 可选改法：给 `collectCreationFlowState` 增加可选入参（如 `units` / `chapterEntries`），由调用方传入已统计结果；`getProjectStatus` 只算一次并复用给 flow。
- 预期：长篇阶段刷新 5→2、短篇/剧本 3→1（旧结构 5→2）。
- 风险：需改 `ui/services/agent-port.ts` 与 `ui/full-writer/creation-flow-state.ts` 签名；`agent-port-status.test.ts` 目前整体 mock 了 `collectCreationFlowState`，改动后需补「传参复用」断言。属 Trae 文件集，可实施，但应单独一轮做，不与 A1/A2 混。

不建议在无真实卡顿证据前做「阶段面板短 TTL 缓存」：会引入显示滞后与多视图不一致，收益不确定。
