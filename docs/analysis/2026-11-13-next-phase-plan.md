# 下一阶段完整计划（2026-11-13）

> 用户定调：三个候选方向（视图内编辑事实 / 更多功能接第二意见 / 真实长篇端到端验证）都重要，
> 但**整个插件目前还没有完整的项目化标准约束**——先出完整计划再动手。
>
> 本计划据此重排顺序：**先把"项目标准"立起来，其余三项都挂在它上面做**。

## 零、现状诊断（为什么"项目化标准约束"必须先做）

### 已有

| 能力 | 位置 | 覆盖 |
|---|---|---|
| 目录约定 | `shared/paths.ts`（20+ 个 `pj*Dir` / `pj*File`） | 分散在函数里，无单一声明 |
| 项目体检 | `services/project-health-service.ts` | **仅 4 类**：duplicate-body / unsettled / bad-frontmatter / orphan-body |
| 事实库 | `<项目>/04-项目总控/一致性审核/事实库.json` | 无结构校验、无版本字段 |
| 项目创建 | 模板脚手架（56 个模板文件） | 创建时合规，创建后**无持续约束** |

### 缺什么（直接后果）

| 缺口 | 后果 |
|---|---|
| 没有「项目标准」的单一真相源 | 目录/文件/命名靠各模块自觉，新增功能容易写出第二套约定 |
| 体检只覆盖章节层 | 结构缺目录、缺必备文件、摘要缺失、事实库损坏**都不会被发现** |
| 没有项目级门禁 | 只能在真实使用中踩坑（本会话已踩：无摘要项目 0 产出） |
| 没有标准版本与迁移 | 升级后旧项目是否"合规"无法判断，也不知道要补什么 |
| 三方向缺乏统一验收口径 | 视图编辑、扩面、长篇验证各自为政，无法回答"整体是否更可靠" |

## 一、总体路线（四阶段，按依赖排序）

```
阶段 A：项目标准约束（schema + 体检 + 门禁 + 迁移）
     ↓（提供统一的"合规"与"数据完整性"基础）
阶段 B：视图内编辑事实（在标准之上做编辑，避免编辑出不合规数据）
     ↓
阶段 C：第二意见扩面（能力扩展，用 B 的视图做人工核对闭环）
     ↓
阶段 D：真实长篇端到端验证（用 A 的体检与门禁做量化验收）
```

## 阶段 A：项目化标准约束（P0，最优先）

### A1. 单一标准源 `shared/project-standard.ts`

声明式定义（数据化，不散落在函数里）：

```ts
export interface ProjectStandard {
    /** 标准版本（用于迁移判断） */
    version: 1;
    /** 必备目录（缺失 = error） */
    requiredDirs: Array<{ path: string; template?: string }>;
    /** 必备文件 */
    requiredFiles: Array<{ path: string; template?: string; optional?: boolean }>;
    /** 命名规范（可校验的正则） */
    naming: Array<{ pattern: RegExp; scope: string; description: string }>;
    /** 章节状态机允许值 */
    chapterStatuses: readonly string[];
}
```

必备目录取自现有约定（保持兼容，不新造第二套）：

```
01-世界架构/{人物,势力,地点,物品}
02-时间线与伏笔
03-大纲与章节/{正文,分卷大纲,步骤结果}
04-项目总控/{剧情记忆,故事台账,一致性审核}
.project（元数据）
```

### A2. 结构校验 `services/project-standard-service.ts`

```ts
validateProjectStandard(app, project): Promise<StandardReport>
```

输出与既有 `ProjectHealthReport` **同一形状**（`issues[]` + `summary`），
新增问题类型：

| kind | 含义 | 严重度 |
|---|---|---|
| `missing-dir` | 必备目录缺失 | error |
| `missing-file` | 必备文件缺失 | error |
| `bad-naming` | 章节/实体文件命名不符规范 | warning |
| `digest-missing` | 有正文但无章节摘要（**本会话踩过的坑**） | warning |
| `fact-store-invalid` | 事实库 JSON 损坏/结构非法 | error |
| `fact-store-version` | 事实库版本低于当前标准 | warning |
| `standard-outdated` | 项目标准版本落后 | warning |

**关键**：`digest-missing` 与本会话的「无摘要项目 0 产出」直接对应——把它变成可发现的问题，而不是靠用户猜。

### A3. 项目级门禁 `scripts/check-project-standard.mjs`

- 对 vault 内所有项目跑 `validateProjectStandard`（通过 `obsidian eval` 或独立 Node 解析 md）
- 可在 `check:prod` 中作为一步（`--no-ai` 下也成立）
- **不阻断写作用户**：只报告，不自动改文件（除非显式 `--fix`）

### A4. 文档与迁移

- `docs/handbook/07-project-standard.md`：标准定义、如何自查、如何修
- 版本迁移：`standard-outdated` 时给出**逐条修复清单**（缺什么补什么）

### 验收

| 项 | 标准 |
|---|---|
| 标准源唯一 | 目录/文件约定只在 `project-standard.ts` 声明；`paths.ts` 的 `pj*Dir` 改为引用它 |
| 体检覆盖面 | 7 类问题各有单测（含"不应报"负例） |
| 门禁 | `check:project-standard` 在真实 vault 上跑通，0 误报 |
| 用户可修 | 每类问题都给「怎么修」的一句话 |

## 阶段 B：视图内编辑事实（P1）

### B1. 编辑能力（小而准）

`ui/fact-store-modal.ts` 扩展：

| 操作 | 说明 |
|---|---|
| 删除单条事实 | 误抽的事实直接删（写回 JSON） |
| 改值/改有效区间 | 行内编辑（值、validFrom、validTo、置信度） |
| 标记「忽略」 | 保留但排除出第二意见（新增 `ignored: true` 字段） |
| 重建本章 | 传 `force=true` 调 `maintainChapterFacts` |

写入路径统一走 `fact-store.saveFactStore`（已有：读失败拒绝写、目标存在直接覆盖）。

### B2. 编辑后的数据完整性（依赖阶段 A）

- 写入前跑一次「事实结构校验」（与 A2 的 `fact-store-invalid` 同一套规则）
- 非法数据**拒绝写入**并说明原因（不允许 UI 把库写坏）

### B3. 变更留痕

每次编辑记录 `updatedAt` 与 `editedBy: 'user'`（事实库已有 `updatedAt`），
便于后续判断"这条是人改的还是模型抽的"。

### 验收

| 项 | 标准 |
|---|---|
| 三个操作可用 | 删除 / 编辑 / 重建本章各有一条端到端验证 |
| 写坏不了 | 非法值被拒 + 事实库保持原样（回归锁） |
| 纯逻辑有测试 | 编辑逻辑抽 `ui/fact-store-edit.ts`，≥12 条测试 |

## 阶段 C：第二意见扩面（P2）

### C1. 待接功能（按价值排序）

| 功能 | 现状 | 接入方式 |
|---|---|---|
| **人物能力/修为** | frontmatter 读取 + 规则比对 | `adviseState`（已有）——需等级序，避免"进阶=矛盾" |
| **物品持有** | 正则匹配"拿出/失去" | `adviseState` + 有效区间（已丢物品不应再出现） |
| **势力归属** | frontmatter 比对 | `adviseState`（转投门派是合法变化，靠区间区分） |
| 地理距离 | 正则抽地名 | `adviseState`（可选，价值较低） |

### C2. 统一接入模式（避免每次重写）

```ts
// 每次接入只需三行：
const advisor = await createStateAdvisor(app, project);
const advice = advisor.advise({ subject, predicate, chapter, value });
if (advice.status === 'consistent') return; // 抑制
```

**要求**：所有接入点必须经过 `quality-gate` 或等价入口透传（本会话已踩"回调无人提供=死代码"）。

### 验收

| 项 | 标准 |
|---|---|
| 每个接入点有单测 | 一致/未知/冲突三态各一条 |
| 无死代码 | 用 `check:command-handlers` 的思路做一次"回调是否有生产调用方"自查 |
| 误报不上升 | 用阶段 D 的注入集对比接入前后 |

## 阶段 D：真实长篇端到端验证（P3）

### D1. 样本与真值

- **真实集**：一部完整作品（如《将夜》前 100–200 章），人工标注真矛盾清单（预期很少）
- **注入集**：在真实原文上人工注入 10 处矛盾 + 10 处合法变化（延续既有 6+3 方法，扩展到 20）

### D2. 指标（延续已有口径）

| 指标 | 定义 |
|---|---|
| 召回 | 注入集检出 / 注入总数 |
| 误报率 | 真实集报告中非真矛盾占比 |
| CED | 每万字符错误数（已有 `consistency-metrics`） |
| 成本 | 拆解 + 判定 token 花费 |
| 事实库规模 | 章节数 / 事实条数 / 主体数 |
| **规模效应** | 误报率随章节数（30 → 100 → 200）的变化曲线 |

### D3. 验收

| 项 | 标准 |
|---|---|
| 召回 | ≥ 8/10（注入集） |
| 误报 | 真实集 ≤ 3 处非真矛盾 |
| 规模效应 | 误报率不随章节数显著上升（否则说明累积策略有问题） |
| 报告 | 一份可复现的报告，含命令与数据文件路径 |

## 二、优先级与工作量估算

| 阶段 | 内容 | 预计规模 | 依赖 |
|---|---|---|---|
| **A** | 项目标准约束（schema/校验/门禁/文档） | 1 个模块 + 1 服务 + 1 门禁 + 文档 | 无 |
| **B** | 视图内编辑（含校验与留痕） | 1 个 UI 模块 + 1 个纯逻辑 + 测试 | A 的校验规则 |
| **C** | 第二意见扩面（3 项） | 3 处接入 + 测试 | A/B 稳定后 |
| **D** | 长篇端到端验证 | 脚本 + 报告（含真实 LLM 成本） | A（体检）+ C（能力） |

**建议顺序**：A → B → C → D。理由：
- A 是一切的基础（没有标准，B 可能写坏数据、D 无法量化"合规"）
- B 依赖 A 的校验规则
- D 是最终验收，必须等 A/B/C 完成

## 三、红线（延续既有）

1. **标准不新增第二套约定**：与 `paths.ts` 现有目录一致，只做收敛
2. **体检只报告不自动改**：改用户文件需要显式 `--fix`
3. **编辑不允许写坏库**：非法数据拒绝写入（与 `saveFactStore` 的"读失败拒绝写"同源思想）
4. **第二意见无生产调用方 = 死代码**：每个新回调必须有透传入口
5. **真实长篇验证必须可复现**：命令 + 数据文件 + 报告三者齐全
