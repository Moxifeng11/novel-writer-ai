# 真实原著验证结论 + LLM 知识库方案实验设计（2026-11-13）

> 起因：用户指出「死板的代码正则不可能完全分析到位，必定需要 LLM 参与」，
> 要求先验证当前代码能力，再实验 LLM + 知识库拆解能否提升准确性。

## 一、当前代码能力的真实边界（已验证）

### 做了什么

用 vault 内 `小说原著下载/将夜.txt`（GBK，6.3MB，**1116 章**）做规模验证：

- GBK → UTF-8 转码，按「第X章」切分成功（1116 个标记）
- 取前 60 章（16.1 万字符）建项目、跑真实命令

### 结果：**0 产出**

```
矛盾总数: 0
CED: 0 / 字符 0
高风险段: 0
```

### 根因（这是本节最重要的发现）

**当前一致性审核的断言来源高度依赖 LLM 生成的章节摘要**：

| 数据源 | 谁产生 | 真实原著有无 |
|---|---|---|
| `ChapterDigest.facts[]`（新事实） | **LLM 摘要** | ❌ 无 |
| `ChapterDigest.timeSpan` | LLM 摘要 | ❌ 无 |
| `CharacterFrontmatter`（年龄/外貌） | 作者手填 | ❌ 无 |
| 台账事件 | 结算流程 | ❌ 无 |
| 正文（仅用于 offset 与视角检测） | 原文 | ✅ 有 |

所以对「只有正文、没有摘要」的原著：

- 规则层几乎没有可比对的断言 → **0 矛盾**
- 连正文派生的「视角混乱」也因章节枚举为空而没跑起来（待修）

### 结论

用户判断成立：**纯正则 + 纯规则层拿不到原著里的深层矛盾**。
不是因为规则写得少，而是因为**没有结构化中间层**——正则只能抽到「十八岁」「持续三日」这种表层的、
带固定句式的信息；而原著里真正的一致性问题是「他知道了他不该知道的事」「这条设定在第 300 章被破坏」，
必须先把正文理解成**结构化事实**才谈得上比对。

这正好是本项目既有的架构分工：

```
正文 →[LLM 摘要/拆解]→ ChapterDigest（facts/events/involved）
                          ↓
        规则层（零成本、可解释、可回归）→ 矛盾
                          ↑
                    断言库（可累积、可复查）
```

**规则层不是替代 LLM，而是消费 LLM 的产物。** 之前验证的 100% 召回，是在「摘要已存在」的前提下测的。

## 二、实验设计：LLM + 知识库拆解能否提升准确性

### 假设

把「摘要」升级为「**知识库式拆解**」（不只是 facts 数组，而是带类型、主体、时间锚、可信度的结构化条目），
配合既有规则层，能在真实原著上把召回显著提升，同时靠「证据链 + 置信度分级」控制误报。

### 三个对照臂（同一批章节，同一套注入矛盾）

| 臂 | 输入 | 判定 | 预期 |
|---|---|---|---|
| **A 现状**（基线） | 无摘要，仅正文 | 规则层 | 召回 ~0（已实测） |
| **B 摘要版** | LLM 生成当前格式 `ChapterDigest` | 规则层 | 召回回升，但受 facts 粒度限制 |
| **C 拆解版** | LLM 按知识库 schema 拆解（见下） | 规则层 + 类型化配对 | 预期最高 |

### C 臂的拆解 schema（每条事实一个条目）

```json
{
  "id": "F-<hash>",
  "type": "age|location|possession|ability|relationship|timeline|world-rule|knowledge|memory",
  "subject": "宁缺",
  "predicate": "age",
  "value": "十七",
  "numeric": 17,
  "unit": "岁",
  "validFrom": { "chapter": 3, "inStoryTime": "春季" },
  "validTo": null,
  "confidence": 0.9,
  "quote": "宁缺今年十七",
  "offset": 1523,
  "source": "llm-decompose-v1"
}
```

关键差异（相对现有 `facts: string[]`）：

1. **类型化**——`type` 决定用哪条配对规则，而不是靠正则猜；
2. **时间有效区间**——`validFrom/validTo` 让「合法变化」自然不报（进阶前后各一段有效期），
   从根上解决「值不等即矛盾」的误报问题；
3. **可累积知识库**——同一条事实在后续章节可被「延续/修正/撤销」，而不是每次重新抽；
4. **字符偏移**——支持一键跳正文（已有能力）。

### 评测方法

1. **注入集**：在真实原文里选定 20 个可验证点，人工注入 10 处矛盾（年龄/位置/持有物/时间线/设定规则各 2 处）
   + 10 处**合法变化**（进阶/迁移/物品损耗/回忆倒叙）。
2. **真实集**：原文前 200 章不注入，人工标注「真矛盾」清单（预期很少，1–3 处），
   主要看**误报数**（假阳性）。
3. **指标**：召回、误报率、CED、每万字成本（token）、单章耗时。

### 成本估算

| 项 | 估算 |
|---|---|
| 拆解 1 章（约 2700 字） | 输入 ~4k tokens，输出 ~1k tokens |
| 200 章 | 输入 ~80 万 tokens（可批处理/缓存） |
| 按 DeepSeek 定价 | 约 1–2 元量级 |
| 分类/配对 | 规则层，零 token |

### 实施顺序（建议）

| 步骤 | 内容 | 验收 |
|---|---|---|
| 1 | 定义拆解 schema + prompt + 严格 JSON 校验（已有 `parseJudgeResponse` 可复用） | 单章拆解产出 ≥5 条合法条目 |
| 2 | 实现 `knowledge-base-decompose.ts`（LLM → 条目）+ 落盘 | 200 章拆解成功率 ≥95% |
| 3 | 断言模型扩展：支持 `validFrom/validTo` 与类型化配对 | 合法变化注入集误报 = 0 |
| 4 | 三臂对照跑评测 | C 臂召回 > B 臂 > A 臂，误报不升 |
| 5 | 把注入集固化为 CI 夹具 | 后续改动可回归 |

## 三、还需要修的（与本次验证直接相关）

1. **章节枚举为空**：PowerShell 创建的项目跑审核得到 `charCount=0`。
   需查 `consistency-audit-wiring` 的正文索引逻辑为何没识别到文件
   （可能是依赖 vault 索引与外部创建文件的时序，或路径前缀匹配问题）。
2. **无摘要时的显式降级提示**：当前无摘要 = 静默 0 产出，用户会以为"没问题"。
   应改为「未找到章节摘要，本次未做事实比对」的 warning（`warnings[]` 已有通道）。

## 四、一句话结论

- **当前代码能力**：在「摘要已存在」时召回 100%/误报 0%（构造集）；
  对**无摘要的真实原著几乎无产出**——证明纯正则不够，符合用户判断。
- **LLM 知识库拆解是对的方向**，但价值不在"让 LLM 判矛盾"（不可控、不可回归），
  而在"**让 LLM 把正文变成可被确定性规则消费的结构化事实**"。
  这样既能拿到深层语义，又保留规则层的可解释、可测试、零成本重复运行。
