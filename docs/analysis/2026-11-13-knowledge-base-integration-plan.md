# 知识库 + LLM 判断：正式接入方案（2026-11-13）

> 用户定调：**正则只做候选，判断交给 LLM + 知识库**；知识库同时作为写作参考（RAG），
> 保障时间线、伏笔、实体状态不崩坏，从而保证剧情逻辑不出错。
>
> 本文是落地路线，不再讨论"要不要做"。

## 一、三层架构（已定）

```
正文 / 摘要 / 人工录入
        ↓  ①拆解（LLM，只在"入库"时花一次钱）
   知识库（结构化事实：主体/谓词/值/有效区间/引文/章节）
        ↓  ②检索（零依赖字段检索，后续可换向量）
   ③判断层（规则优先 → 不确定的候选交 LLM，严格 JSON + 理由门槛）
        ↓
   审核报告 / 写作参考 / 既有功能第二意见
```

**关键分工**：
- **拆解**：LLM 花一次钱，产物落盘可复用、可人工修正；
- **检索**：不走网络，按主体/类型/章节窗/关键词查；
- **判断**：确定性规则先跑，只有规则判不了的候选才调 LLM（阶段三实测：144 候选 ¥0.04）。

## 二、已完成（可复用）

| 模块 | 作用 | 测试 |
|---|---|---|
| `engine/consistency/knowledge-decompose.ts` | 正文 → 结构化事实（quote 必真、有效区间、严格校验） | 18 |

误报 165 → 0（归一化 + 判定）；全链路 ¥0.34/30 章。

## 三、接入路线（按依赖顺序）

### P0 落盘与调用链（本批）

1. `shared/paths.ts` 增加 `pjKnowledgeBaseFile(project)` →
   `<项目>/04-项目总控/知识库/事实库.json`
2. `engine/consistency/knowledge-service.ts`：
   - `loadKnowledgeBase(fs, project)`（3 态：ok / missing / read-failed，同 assertion-store 模式）
   - `decomposeAndAppend(app, plugin, project, chapterKey, body)`：调 `knowledge-decompose`
     → `appendFacts` → 原子写（**目标存在则 write**，避免 rename 覆盖崩溃）
   - `ensureChapterFacts(project, chapter)`：已拆解过就跳过（按章去重）
3. 一致性审核消费知识库：`consistency-audit-wiring` 增加 `loadKnowledgeFacts`，
   把事实转成断言并入既有规则层（`entriesToAssertions`）
4. 结算流程：步骤 19（摘要）之后追加「拆解入库」（无摘要也能拆正文）

### P1 判断层接入（本批后续）

5. `engine/consistency/judge-pipeline.ts`：
   - 规则层产出候选 → `filterEquivalentCandidates` → `buildJudgePrompt` → `parseJudgeVerdicts`
   - 只在候选数 > 0 且开关开启时调用；成本上限可配（默认 3 批 × 12 条）
6. 审核报告新增字段：`llmJudgedCount` / `llmConfirmedCount` / 成本估算

### P2 既有正则功能的"第二意见"（用户核心诉求）

对以下三类**优先接入**（正则最容易出错、且后果最严重）：

| 功能 | 现状 | 接入方式 |
|---|---|---|
| **时间线** | 正则抠「第三日/半个时辰」 | 候选时间点 → 查 `stateAt` 已知时间锚 → 冲突交 LLM 判 |
| **伏笔** | 正则匹配「未回收线索」 | 伏笔文本 → 检索知识库中是否被兑现（keyword 检索 + LLM 判定） |
| **实体状态** | 正则读 frontmatter 修为/位置 | `stateAt(subject, chapter)` 给权威状态，正则只做补充 |

**原则**：正则不再"下结论"，只负责**找候选**；结论来自知识库 + 判断层。
这样既保留正则的零成本与可解释，又补上语义。

### P3 写作参考（RAG 落地）

7. 写作前检索：输入本章大纲/关键词 → `queryFacts`（subject/type/keyword）
   → 组装成「相关设定摘要」注入提示词，替代现在"让模型自己回忆"。
8. 视图：知识库浏览（按主体分组、按章节看状态演变），支持人工修正条目。

## 四、红线（不能违反）

1. **拆解产物必须落盘**，不能只存在内存——否则无法人工修正、无法回归。
2. **判定层不得凭空产出矛盾**：`real=true` 必须带 ≥8 字理由与双侧引文。
3. **LLM 失败一律降级**为规则层结果，不阻断结算/审核。
4. **成本上限**：单次审核的判断调用封顶（默认 36 候选），超出走规则层并标注"未判定"。
5. **知识库不是真相源**：正文才是；知识库与正文冲突时以正文为准并在报告中标注。

## 五、验收标准

| 阶段 | 验收 |
|---|---|
| P0 | 真实项目跑一次结算 → 知识库文件生成 → 再跑审核能读到事实（断言数 > 0） |
| P1 | 注入 5 处矛盾的项目：召回 ≥4/5，误报 ≤1 |
| P2 | 时间线/伏笔/实体状态三类各有一个真实样本被"纠正"（正则判错、知识库判对） |
| P3 | 写作提示词中注入检索到的设定，且不超 token 预算 |
