# P1-2 方案：`autoRevisionAfterQC` 与四项校验对齐（2026-11-25，ZCode）

> 原始表述：*「目前自动修订只看 QualityGate 的 passed；可评估把『四项校验里 format/perspective
> warn 连续两章』纳入是否触发定向修订的判断（会改动自动行为，先给方案再动手）」*。

## 一、现状事实（代码核实，不是转述）

### 1.1 自动修订有两条触发点，都不是「四项校验」

| 触发点 | 条件 | 代码 |
| --- | --- | --- |
| A：步骤 7（正文生成）后 | `!QualityGate.passed && settings.autoRevisionAfterQC` | `engine/step-runner.ts:1743` |
| B：步骤 8（质量控制）完成后 | `settings.autoRevisionAfterQC`（**无条件尝试**） | `engine/step-runner.ts:1794` |

### 1.2 B 的「无条件」不等于「无条件改稿」——内部有闸门

`executeTargetedRevision()`（`engine/step-runner.ts:997`）：
- 无正文 → 报错返回（`:1006`）
- **`parseQualityControlReport(stepResults[QUALITY_CONTROL])` 返回空 → 报错返回（`:1010-1014`）**
- 最多取 8 条、高优先级优先（`:1015-1020`）

所以真正的修改前提是「QC 报告里有结构化质量问题条」。

### 1.3 缺口定位（这才是 P1-2 的真实价值）

**四项校验里的 `format` / `perspective` 是程序检测项，永远不会出现在 QC 报告的 issues 里**
（QC 是 AI 审查输出，格式/视角由 `shared/body-format.ts#analyzeBodyFormat`、
`engine/consistency/extended-rules.ts#detectPerspectiveMix` 程序判定）。
结论：

- 现有自动修订链路**只修 AI 审出的叙事问题**，**永不修「格式偏离 / 视角混用」**；
- 四项校验只进质量面板 + 诊断事件，没有任何动作出口。

因此 P1-2 不是「收紧已有触发」，而是「给程序可检的软问题**新增一个修或提示的出口**」。

### 1.4 附带事实：两个触发点可能对同一章修两次

A（步骤 7 后）若 QualityGate 未通过 → 修一次；B（步骤 8 完成后）再尝试一次。
两者条件不同、时点不同，同章最多两次修订（每次最多 8 条）。这是既有行为，
任何新增触发都必须避免变成第三次。

## 二、三个方案

### 方案 A（推荐）：面板引导，不改自动行为

**做法**：趋势区检出「format 或 perspective 连续两章 warn」时，在质量面板显示一条引导：

> ⚠️ 格式偏离已连续 2 章（第2章、第3章），建议对本篇执行定向修订。

并复用现有「定向修订」按钮路径（用户点击才执行）。

- **触发条件**：`buildFourCheckTrend()` 的结果里，最后两行同一项（format 或 perspective）均为 `warn|fail`。
- **回滚**：无（纯展示，删掉该提示即回滚）。
- **测试口径**：shared 侧断言判定函数（连续两章同项 → true；隔章 → false；不同项 → false）；
  面板接线断言（提示文案来源 shared）。
- **预估**：0.5 天。
- **风险**：用户可能忽略提示（但这正是「不新增阻断点」原则的代价，与既有四项校验定位一致）。

**为什么推荐**：改动为零行为风险；把「是否修」留给用户；且与交接文档「四项校验只警告不阻断」的
决策 1 完全一致（不给正文链路加新阻断/新自动动作）。

### 方案 B：新开关 + 补位触发（默认关）

**做法**：新增 `settings.autoRevisionOnFourCheckTrend`（默认 `false`）。
开启后，在 B 的闸门**失败时**（QC 无 issues）再判断趋势：连续两章同项 warn → 构造一条
synthetic issue（severity: `warn`，message 来自四项校验 item）追加到修订列表再执行。

- 需要改 `executeTargetedRevision` 的签名（接受 externalIssues），或新增入口。
- **不重复**：B 已实际修订（issues > 0）时不再看趋势；A 已修订的同章也不看。
- **回滚**：设置关即可（默认关）。
- **测试口径**：mock QC 空报告 + 连续两章 warn 的四项校验.json → 修订被触发一次；
  QC 有 issues 时趋势不参与；单章 warn 不触发。
- **预估**：1.5 天（含 executeTargetedRevision 的 issue 注入与新设置项 + 设置页）。
- **风险**：新增一条自动改稿路径，即使默认关，开启用户的体验变化需实机验证；
  且「连续两章」的判定依赖前一章报告是否存在（首章无前一章 → 不触发）。

### 方案 C：收紧 B（QC 无 issues 就不尝试）

**做法**：`stepKey === QUALITY_CONTROL` 时先判断 QC 报告是否有 issues，无则跳过调用。

- **回滚**：改回无条件调用。
- **测试口径**：无 issues 时不弹「没有可执行的结构化质量问题」提示（现状是每次都会弹一个错误提示）。
- **预估**：0.5 天。
- **注意**：这个方案**与四项校验无关**，只是顺手清理「每章 QC 完成后必然弹一次
  `showError('没有可执行的结构化质量问题')`」的噪音——如果 QC 经常通过的章节，这会是个小骚扰。
  可作为独立小修，不与 P1-2 绑定。

## 三、结论与建议

1. **P1-2 的真实缺口是「格式/视角没有动作出口」，不是「触发条件太宽」**。
   如果目标是「持续恶化能被处理」，方案 A 就够（用户一键修）；如果目标是「自动修」，才需要 B。
2. 推荐 **A 先做**（0.5 天、零风险），观察用户反馈；若确实需要自动，再上 B。
3. 方案 C 是独立的小噪音清理，建议单独提交（不在 P1-2 scope 内）。
4. 无论选哪个，**都不要改「四项校验只警告不阻断」的决策**（交接文档 §四 决策 1）——
   本方案的任何实现都不得让四项校验进入 `requiredBeats` 或阻断步骤推进。

## 四、实施前需要确认的三件事

1. 选 A / B / C 哪个（或组合）；
2. 若选 B：`autoRevisionOnFourCheckTrend` 的默认值（建议 `false`）；
3. 若选 A：提示文案的触发阈值（建议「连续两章同项 warn|fail」；是否也包含 `fail` 需确认——
   字数 `fail` 是硬门禁已修，格式/视角目前没有 `fail` 态，实际只会是 `warn`）。
