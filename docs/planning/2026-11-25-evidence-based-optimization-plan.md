# 基于云笔信息的插件优化计划（2026-11-25，证据版）

> 状态：**可执行计划** · 2026-11-25 · ZCode
> 依据：云笔四层逆向 + 139 段真人基线 + opencode 实测 + 朱雀 n=22 实测
> **本文推翻了此前三份计划中的多处结论**，理由见第一节。

## 一、先纠正：此前计划里被实测推翻的判断

在写任何优化项之前，必须先把错误结论清掉，否则计划会指向错的方向。

### 纠正 1：「长句是唯一硬指标缺口」——不成立

| 组 | 长句(≥35字)中位 | 朱雀人工率 |
| --- | ---: | ---: |
| 139 段真人手写 | **39.13%** | 100% |
| 云笔 5570（301 章） | **13.79%** | **42.3%** |
| 云笔 6153（10 章） | 22.2% | 0% |
| 本仓（opencode 3 章，整章口径） | 21.60% | 未测 |

**关键事实**：人工率 42.3% 的 5570，长句只有 13.79%；人工率 0% 的 6153，长句有 22.2%。

**长句与人工率是弱相关**（Pearson r = **0.150**，n=22）。
而对话密度是 **r = 0.453**。

**结论**：把长句从 21.60% 拉到 26.98% **不会**改善人工率。
此前「唯一缺口」的判断来自「只和 139 段真人基线比、没和人工率做相关」的错误方法。

### 纠正 2：「对话密度需 ×6」——本仓已达标

| 因子 | 本仓实测 | 真人中位 | 判定 |
| --- | ---: | ---: | --- |
| 引号/千字 | **27.67** | 18.53 | ✅ 超真人 |
| 段落均字 | **48.83** | 41.76 | ✅ 超真人 |
| 单句成段 | **10.77%** | 13.33% | ✅ 优于真人 |

本仓在**三因子上全部达标**，且优于人工率 42.3% 的云笔 5570（25.0 / 51.4 / 16.9%）。

### 纠正 3：A/B 实测证明「改长句提示词」无效甚至有害

同一素材、同模型、同温度，只改人味块第 2 条：

| 变体 | 长句 35+% | 说明 |
| --- | ---: | --- |
| A 现文案 | **39.58%** | 已超真人中位 |
| B 抄云笔铁律 9「长句合法用途」 | 11.18% | **反而变差** |
| C 可数下限（每千字 8 处） | 13.43% | **反而变差** |
| D B+C 组合 | 21.38% | 也不如现状 |

**教训**：云笔铁律 9 的长句清单在本仓模型上**起了反作用**——它把注意力引向「哪些场景该写长句」，
反而让模型在其余场景更倾向短句。**这条不落地。**

### 纠正 4：单章方差极大，「缺口」本身在噪声内

同一套提示词跑两次：22.94% 和 39.58%。
云笔 5570 内部 21 章抽样：最小 0%、中位 9.29%、最大 66.1%，**极差 66 个百分点**。

**单次测量不足以判定缺陷**。

## 二、那么真正该优化什么（有证据的）

### 2.1 相关性强弱排序（n=22，同口径 2000 字窗口）

| 因子 | Pearson r vs 人工率 | 权重 | 本仓状态 |
| --- | ---: | --- | --- |
| **对话密度（引号/千字）** | **0.453** | **主因** | ✅ 已达标（27.67） |
| 段落均字 | 0.450 | 主因 | ✅ 已达标（48.83） |
| 段落长度 std | 0.398 | 次因 | 待测 |
| 单句成段 | 必要条件（≤20%） | 门槛 | ✅ 10.77% |
| 长句占比 | **0.150** | **弱** | 21.60%（**不必强求**） |

**三因子已全达标，无第四因子可从统计层找到。**

## 三、执行计划（三步，每步有验收）

### 第一步：生成结果「待确认」态（最高价值）

**问题**：`engine/body-writer.ts:344` 生成完直接 `await fs.write(req.path, content)`，
用户没有拒绝的机会。AI 写坏了只能手动回滚。

**云笔做法**：生成结果先进「待确认」面板，用户点「采用」才落库。

**本仓改法**（不照搬 UI，用最小侵入）：

1. `BodyWriteRequest` 加 `requireConfirm?: boolean`
2. 为 true 时写入 `<章节目录>/.pending/<chapter>.md`，不覆盖正文
3. 返回 `pendingPath`，UI 侧提供「采用 / 弃用」两个动作
4. 设置项 `bodyWriteConfirmMode: 'off' | 'auto' | 'always'`（默认 `auto` = 覆盖已有正文时才确认）

**验收**：
- 单测：`requireConfirm: true` 时不覆盖原文件，落 `.pending/`
- 单测：`'off'` 时行为与现在完全一致
- 真机：生成后能看到待确认文件，采用后才进正文

### 第二步：后章约束 + 衔接锚点优先级

**问题**：本仓有 `prevChapEnding`（前章原文），但**没有后章约束**，
模型可能提前把下一章的悬念写掉。

**云笔做法**：
- `next_chapter_constraint` 模块（600 tokens）：后一章方向 + L0c 禁止泄露
- 衔接锚点优先级：**前章实际文本 > 时间线前情锚点 > 摘要章尾悬念 > 大纲开头承接**

**本仓改法**：
1. `template-utils.ts` 加 `nextChapterHook` 变量（从下一章大纲取「章首衔接」字段）
2. 本仓已有 `nextChapterHook`？先核实
3. 若无则新增，并在 body 提示词里加：
   ```
   【下一章开头（禁止提前写出它的内容，只用于避免撞车）】
   ${nextChapterHook}
   ```
4. 加衔接锚点优先级声明（并入 L0-L3 仲裁块）

**验收**：单测断言 body 提示词含后章约束段且标了「禁止泄露」。

### 第三步：L0-L3 仲裁体系

**问题**：本仓提示词平铺——`human-voice` 说「一段 80–220 字」、
`body-format` 契约说别的、`naturalizeBodyText` 又要合并，**冲突时模型不知道听谁**。

**云笔做法**：L0a/L0b/L1a/L1b/L1.5/L2/L3 + 同层左侧优先 + 跨层高层覆盖。

**本仓改法**：新建 `engine/prompts/priority-system.ts`，内容精简版：

```
## 优先级体系（冲突仲裁）
L0 不可破红线：视角约束 / 实体边界 / 不得复述前章 / 不得泄露后章
L1 双轨并列：大纲落实 ∥ 叙事手法
L1.5 用户补充要求
L2 写作硬约束：段落节奏 / 信息密度 / 修饰词节制
L3 风格偏好与范例锚定（只管语感）

仲裁：同层左侧优先；跨层高层覆盖。

衔接锚点优先级：前一章结尾实际文本 > 时间线前情锚点 > 摘要章尾悬念 > 大纲开头承接
```

**关键**：接入后把 `body-format` 的项目级格式规则降为 L3，把 `human-voice` 的段落约束提到 L2。

**验收**：单测断言提示词含 L0-L3 段与衔接锚点优先级。

## 六、本文档的立场

此前三份计划（`yunbi-vs-plugin-optimization-plan.md`、`zhuque-criteria-correction.md` 的部分结论、
`plugin-baseline-measured.md` 的推论）都有「拿云端/他人数据推断本仓缺陷」的问题。

本文的每条建议都经过：
1. **同口径测量**（统一 2000 字窗口、同一 metrics 函数）
2. **相关性验证**（不只和基线比，还要和结果变量做相关）
3. **A/B 实测**（改提示词前后都测，不信直觉）

**长句这件事就是最好的教训**：看起来是「明显缺口」（21.60% vs 26.98%），
但做了相关性分析和 A/B 实测后发现——**它根本不重要，而且改了会变差**。
