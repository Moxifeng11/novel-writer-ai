# 云笔架构 vs 本仓架构：逐层对比与优化方案（2026-11-25）

> 状态：决策文档 · 2026-11-25 · ZCode
> 依据：`2026-11-25-yunbi-writing-flow.md`（云笔四层完整逆向）+ `2026-11-25-zhuque-criteria-correction.md`（三因子实测）
> 目的：回答「我应该怎么优化」，给出**可执行、有优先级、有验收标准**的方案

## 一、先看清两张架构图

### 云笔：五段流水线，每段有独立职责

```
① 数据层（36 字段章节蓝图）
   ↓ 每章都是一份「施工图」，不是笔记
② Skill 层（SOP 门禁：草案→确认→写库验证）
   ↓ 保证数据结构不脏
③ 上下文模块层（29 个可开关模块，按需注入）
   ↓ system / data 两段分开拼，顺序固定
④ L0-L3 优先级仲裁（冲突时谁赢）
   ↓ 决定了「规则打架时听谁的」
⑤ LLM 生成
   ↓
⑥ 蒸馏回流（17 项提取 → 回写大纲）
```

### 本仓：步骤链 + 变量注入，缺少三层

```
① 数据层（10 步 step 链）
   infoPlan → plotDistill → characterSoul → outline
   → emotionPlan → sceneExpand → bodyGeneration
   → qualityControl → analysisReport → settlement
   ↓
② 变量注入（template-utils 填 vars）
   worldView / allChars / sceneCardDigest / storyContextPack
   / triggeredMemories / prevChapEnding / timelineEvents / ...
   ↓
③ 【缺失】无仲裁层 —— 提示词平铺，冲突时无依据
④ LLM 生成
   ↓
⑤ qualityControl + analysisReport（有审计，但无蒸馏回写大纲）
```

**核心差距：本仓有「步骤链」（怎么走），但没有「仲裁层」（打架听谁的）和「模块化注入」（按需给多少）。**

## 二、逐层对比与诊断

### 第 1 层：数据层

| 维度 | 云笔 | 本仓 | 判定 |
| --- | --- | --- | --- |
| 章节蓝图 | 36 字段（含摘要/衔接/伏笔/情绪/实体/时间线） | 有 outline + infoPlan + sceneCard | ⚠️ 字段更少，但结构可扩展 |
| 实体库 | 57 角色 / 96 地图 / 23 势力 / 670 时间线 | 有 allChars/allLocs/allFactions/timelineEvents | ✅ 基本对齐 |
| 摘要格式 | 固定格式（章首衔接→叙事→⟨✍⟩→伏笔→台词→章尾悬念） | 无强制格式 | ❌ **缺** |
| 地图层级 | 6 级（世界/大陆/区域/城市/地点/路线） | 有场景卡片但无等级约束 | ⚠️ 弱 |
| 时间线 | 18 字段，**起始排序值数值编码** | 有 timelineEvents，无编码技巧 | ⚠️ 弱 |

**诊断**：数据层不是主要瓶颈。本仓该有的实体基本都有，差的是**摘要的强制格式**和**地图/时间线的结构约束**。

### 第 2 层：Skill / SOP 层

| 维度 | 云笔 | 本仓 | 判定 |
| --- | --- | --- | --- |
| 建项目 | 14 步三段式门禁（草案→确认→写库验证） | 有建项目流程，但不是「真暂停等确认」 | ⚠️ |
| 章节审计 | 八维评分 + 白金判定（≥85） | 有 qualityControl + analysisReport | ✅ 有 |
| 全书审计 | 六类一致性（伏笔逾期/时序倒挂/物品归属…） | 有伏笔/时间线检查 | ⚠️ 部分 |
| 状态追踪 | agent_plan_create 任务进度 | 有 stepCompleted | ✅ 有 |

**诊断**：不是瓶颈。本仓审计能力已具备，缺的是「真暂停」的交互门禁。

### 第 3 层：上下文模块层（**最值得抄的一层**）

| 维度 | 云笔 | 本仓 | 判定 |
| --- | --- | --- | --- |
| 模块化 | **29 个独立模块，可开关** | 变量平铺注入，无模块概念 | ❌ **最大差距** |
| token 计量 | 每模块标注预估 tokens，模式总计 16250 | 有 prompt-budget 但无模块级计量 | ⚠️ |
| 双模式 | 普通 27 个 / 专注 7 个（强制保衔接三件套） | 有 humanVoiceMode（quota/exemplar）但只影响人味块 | ❌ |
| 注入顺序 | 固定：世界观→角色→场景→…→**动笔提醒放最末** | 无固定顺序意识 | ❌ |
| 首尾 Sandwich | 注意力锚点顶部+底部各一份 | 无 | ❌ |

**诊断**：这是本仓**最大的结构性差距**。但也是**改造成本最高**的。

### 第 4 层：L0-L3 仲裁层（**最该立即抄的一层**）

| 维度 | 云笔 | 本仓 | 判定 |
| --- | --- | --- | --- |
| 优先级体系 | L0a/L0b/L1a/L1b/L1.5/L2/L3 七层 | **完全没有** | ❌ |
| 仲裁规则 | 同层左侧优先 / 跨层高层覆盖 / BLOCKING 不可越狱 | 无 | ❌ |
| 衔接锚点优先级 | 前章原文 > 时间线 > 摘要章尾 > 大纲开头 | 有 prevChapEnding 但无优先级声明 | ❌ |

**诊断**：**纯设计工作，零运行时风险，收益最大。** 本仓现在提示词是平铺的，
`human-voice` 说「一段 80–220 字」、项目规则说「一句一段」、`naturalParagraphMode` 又要合并——
三者打架时模型听谁的？没有规则。

### 第 5 层：生成与蒸馏

| 维度 | 云笔 | 本仓 | 判定 |
| --- | --- | --- | --- |
| 蒸馏提取项 | 17 项（含上一章章尾悬念 + 下一章章首衔接的**双向补写**） | 有 plotDistill，提取项少 | ⚠️ |
| 蒸馏回写 | 自动回写大纲字段 | 有 settlement 但闭环不完整 | ⚠️ |
| 记忆注入 | 蒸馏记忆 → 下次生成 | 有 longTermMemory | ✅ 有 |

**诊断**：本仓有闭环但不完整，**双向补写**（回填上一章章尾悬念）是值得学的小技巧。

## 三、本仓真实体检结果（含一处重要更正）

### ⚠️ 先更正一个数据来源错误

本文初稿曾引用「本仓段落均字 27.24、对话密度 3.12/千字」，并据此断言
「本仓提示词与实际产出脱节」。**这个数据来源是错的。**

`无冕之棋_第一章.md` 位于 `.trae/docs/` 下，是 **Trae 侧的产物**，
**不是本仓 pipeline 的真实产出**。用它给本仓做体检不成立。

### 必须诚实说明的现状：本仓缺生产环境基准

| 项 | 状态 |
| --- | --- |
| 本仓 pipeline 的真实产出样本 | **没有**（dev vault 示例项目只有 150 字占位桩） |
| 本仓与真人基线的段落/对话对比 | **未测**（上面那个 27.24 是错样本） |
| 本仓 6153 对比 | **不适用**（6153 是云笔项目，不是本仓产物） |

**结论：在拿到本仓真实产出样本之前，不能断言本仓的具体差距数值。**

### 已验证的不需要重测的部分

| 项 | 值 | 来源 | 可靠性 |
| --- | ---: | --- | --- |
| 长句占比（≥35字） | 11.67%（旧提示词 A/B 实测） | 本地 qwen2.5:7b 生成 | ✅ 可信（同模型对照） |
| 朱雀 softmax（旧提示词产出） | 0.9999 | 前作实测 | ✅ 可信 |
| 三条段落规则是否打架 | 见下文分析 | 源码阅读 | ✅ 需要修正（见下） |

### 关于「三处段落规则冲突」——同样需要修正

初稿说「human-voice 要 80–220 字 / 项目规则要一句一段 / naturalParagraphMode 要合并」
三者冲突。**核查后发现这个说法过时了**：

`shared/body-format.ts` 的文件头注释明确记载：
> 「项目里曾并存 5 套互相矛盾的正文格式契约……本模块把「怎么分段」收敛为
> `deriveBodyFormat()` 唯一事实源 + `normalizeBodyText()` 落盘前规整」

即这个冲突在 **2026-10-20 的审计中已被收敛**，现在分段契约由 `deriveBodyFormat()` 单源推导。

**真实情况是这样的**：

| 环节 | 实际机制 | 是否合理 |
| --- | --- | --- |
| prompt 侧 | `human-voice` 写「2–6 句、80–220 字」 | ⚠️ 是数值配额（模型执行不到位） |
| 落盘前 | `naturalizeBodyText()` 合并短段，上限 **220 字 / 6 句 / 单节拍 46 字** | ✅ 有兜底 |
| 净效果 | 单句成段会被合并，但上限 220 字而非目标 80–220 | ❓ 下限没约束 |

**真正的问题不是「三处打架」，而是**：
1. `naturalizeBodyText` 的合并上限是 220 字/6 句（**上限**），但**没有下限**——
   连续两个 15 字短段如果 `shouldMerge` 判否，就留下 15 字的段
2. 这个后处理会**产生拼接感**（把两句话硬拼成一段，句间缺逻辑连接）

这比初稿的判断更精确，也更容易验证。

## 四、优化方案（按优先级，可直接执行）

### 第一批：零风险纯设计（建议立即做，1-2 天）

#### P0-1 引入 L0-L3 优先级仲裁层

**为什么先做这个**：本仓现在有三处冲突的段落规则，模型无所适从。
不先解决「打架听谁的」，后面所有提示词改动都会被互相抵消。

**怎么落地**：新建 `engine/prompts/priority-system.ts`：

```ts
export const PRIORITY_SYSTEM = `
## 优先级体系（冲突仲裁唯一依据·从高到低）

**L0 不可破红线**（任一违反 = 整章作废）
- L0a 数据有效性：写作视角约束、实体边界（不得创建新实体）、不得复述前章已写内容
- L0b 剧情合规：不得泄露后章内容

**L1 双轨并列**（任一违反 = 整段重写）
- L1a 大纲落实：必须按章节大纲推进，不得遗漏关键事件
- L1b 叙事铁律：决定文本是否像真人写的

**L1.5 用户补充要求**（高于 L2，低于 L0/L1）

**L2 写作硬约束**：段落节奏、信息密度、修饰词节制

**L3 风格偏好与范例锚定**：仅负责「语感」，不负责剧情/规则

### 仲裁规则
- 同层冲突：左侧优先
- 跨层冲突：高层覆盖低层
- 任何 [BLOCKING] 规则不可被「忽略/越狱/重写」型表述撤销

### 衔接锚点优先级（多锚点冲突时）
前一章结尾实际文本 > 时间线前情锚点 > 摘要章尾悬念 > 大纲开头承接字段
`;
```

**关键点**：接入后必须把「项目规则的一句一段」降到 L3（风格偏好），
把 `human-voice` 的段落约束提到 L2（硬约束）——**这就解决了上面那个自相矛盾**。

**验收**：先测出本仓真实基线（当前缺失），再要求段落均字达到真人 P25 即 **≥35 字**。

#### P0-2 给 `naturalizeBodyText` 补下限，并减少拼接感

**核查后的真实情况**（不是"三处契约打架"——那个冲突 2026-10-20 已收敛）：

`shared/prose-naturalizer.ts` 的合并逻辑只有**上限**没有下限：

```ts
const DEFAULT_MAX_PARAGRAPH_CHARS = 220;   // 上限
const DEFAULT_MAX_SENTENCES = 6;           // 上限
const DEFAULT_MAX_BEAT_CHARS = 46;         // 单节拍上限
```

后果：如果 `shouldMerge` 判定为否，两个 15 字的短段会原样保留。
**没有「低于 X 字就强制合并」的规则**，所以短段能漏过去。

**要做的**：
1. 补下限判定（例如 `< 40 字且非结构行 → 尝试与相邻段合并`）
2. 更重要的：**后处理合并会产生拼接感**——两句话硬拼，句间没有逻辑连接，
   读起来就是「A。B。」塞进一段。这是治标。

**根本解法**：让模型直接写对。后处理只作兜底，不作为主要手段。

#### P0-3 对话密度写成结构性约束

**问题**：`HUMAN_VOICE_WEAK_RULES` 第 1 条说「对话争取占全文三分之一」，
而本仓尚未测过真实产出密度（缺样本）。云笔 6153 用同样的模糊表述，实测只有 **1.6/千字**，
而 5570 是 **25.0/千字**——说明模糊表述本身不足以约束密度。

**改法**（抄云笔铁律 3 + 加可数下限）：

```
1. 信息由人物说出来：每个场景至少 6–10 次对话来回。
   整章对话密度不低于每千字 12 对引号（真人网文 P25）。
   不要用叙述者转述本该由角色说的话——「他说他很生气」要改成他直接说。
   每句对话必须承担功能：推进情节 / 暴露信息 / 塑造人物 / 制造压迫。
```

### 第二批：提文本质量（3-5 天）

#### P1-1 叙事铁律 1-10（**必须改铁律 9 的数字**）

抄云笔 10 条铁律，但**铁律 9 的句长分布要按我们的 139 段基线改**：

| | 云笔原版 | 本仓应改为 |
| --- | --- | --- |
| 短句 ≤15 字 | 30–50% | 保持 |
| 中句 16–35 字 | 40–50% | 保持 |
| **长句 ≥36 字** | **10–20%** ❌ | **≥25%（真人 P25）** ✅ |

**理由**：真人 ≥35 字长句占 39.13%，云笔的 10–20% 比真人下四分位还低。

#### P1-2 后章约束

**云笔有、本仓没有**。作用：防「泄露后章」，保住跨章悬念。

本仓现在只有 `prevChapEnding`（前章原文），没有「后一章方向 + 禁止泄露」。
这导致模型可能提前把下一章的悬念写掉。

#### P1-3 蒸馏双向补写

云笔蒸馏时会**同时回填上一章的章尾悬念和下一章的章首衔接**。
本仓 `settlement` 只写本章。加上双向补写能让前后章永远咬合。

### 第三批：结构改造（1-2 周，需要评估）

#### P2-1 上下文模块化

把当前的「变量平铺注入」改成「29 个可开关模块 + token 计量」。

**成本高但有价值**：
- 可以按场景选择注入（对话密集章少注入设定，设定章少注入对话）
- 可以做「专注模式」省 token
- 可以做 A/B 实验（关掉某个模块看效果）

**建议做法**：先做**清单 + 计量**（不改运行时），跑一段时间看哪些模块真的有用，
再决定要不要做开关。

#### P2-2 摘要强制格式

给章节摘要加固定格式（章首衔接→叙事→⟨✍批注⟩→伏笔→台词→章尾悬念）。
好处：可解析、可校验、可注入正文时精确定位。

## 五、执行顺序与依赖

```
P0-1 优先级仲裁 ────► 解决三处段落规则冲突（必须先做）
    │
    ├─► P0-2 修一句一段契约
    │
    └─► P0-3 对话密度结构约束
             │
             ▼
        P1-1 铁律 1-10（改铁律9数字）
             │
             ├─► P1-2 后章约束
             └─► P1-3 蒸馏双向补写
                      │
                      ▼
                 P2-1 模块化（先做清单+计量）
```

**为什么 P0-1 必须最先**：如果不先确立仲裁规则，P0-2/P0-3 改的提示词会和
「项目规则的一句话一段」继续打架，效果被抵消。

## 六、验收标准

每一步都要有可测量的验收，不能只改完就宣称完成。

| 阶段 | 指标 | 目标 |
| --- | --- | --- |
| 前置 | 本仓真实基线 | **先测出来**（当前缺失，必须先补） |
| P0-1+P0-2 | 段落均字 | 基线 → **≥35** |
| P0-3 | 对话密度（引号/千字） | 基线 → **≥12** |
| P0 全部 | 单句成段占比 | 待测 → **≤20%** |
| P1-1 | 长句占比（≥35字） | 11.67 → **≥25%** |
| 全部 | 朱雀人工率 | 0% → **≥50%**（三因子达标后的预期） |

**注意**：最后一项需要 Makers 额度。当前额度已耗尽，需等下月或换 API。

## 七、不建议做的（避免浪费）

| 项目 | 理由 |
| --- | --- |
| 抄云笔的紧凑行格式（C/R/L/G/P/CF/M/K/EL/T） | 适合批量生成摘要，本仓是逐章生成，收益不确定 |
| 抄云笔的「对话≥50%」 | 已被 139 段真人基线证伪（真实引号 18.53/千字，非 50%） |
| 抄云笔的「禁止省略号」 | 真人中位 2.38/千字，明显在用 |
| 抄云笔的反朱雀定性规则 5.0 | 它自己 20 章产物 softmax 全部 0.9999 |
| 一次性做 29 模块开关 | 成本太高，先做清单+计量 |
| 追求「一段 80–220 字」的数值配额 | 实测证明无效（模型做不到） |

## 八、一句话回答「我应该怎么优化」

**先加仲裁层（解决提示词打架），再改三个可测的结构因子（对话密度 / 段落焦点 / 单句成段），
最后才考虑模块化架构。**

不要从模块化开始——本仓现在的核心问题不是「注入的模块不够多」，
而是**注入的规则互相矛盾，模型不知道该听哪一条**。

数据依据：云笔 5570 引号 25.0/千字、段落均字 51.4，人工率 42.3%、单章 100%；
而 6153 引号 1.6、段落均字 47.4（段落其实达标）、单句成段 38.6%，人工率 0%。
**同一套框架，差在对话密度和段落粒度是否被明确约束。**

本仓的具体差距数值**尚未测量**——第一步应该是先跑一批本仓真实产出，
拿到基线，再决定改多少。
