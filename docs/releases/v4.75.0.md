# v4.75.0 — 移除从未可用的批量拆解模态

发布日期：2026-11-08

## 为什么发这一版

全仓审计把「批量拆解」判为缺陷方向待定：`ui/batch-deconstruct-modal.ts` 从 `plugin.deconstructionWorkerManager` 取依赖，而**该属性在插件上从不存在**——`DeconstructionWorkerManager` 是 `DeconstructionScheduler` 的私有字段（`engine/deconstruction-scheduler.ts:239`，构造函数内自建 `:281`），全仓唯一引用就是这条模态。用户选第一个文件必然 TypeError；即使强行补齐依赖，结果也只存在内存 `partialResult`，`viewResult` 仅弹一条 Notice，从不落盘。

用户拍板 ③b：**删除模态、命令改指真实入口**，而不是给同一能力开第二扇门。

## 主要变化

### 1. 删除 `ui/batch-deconstruct-modal.ts`（409 行）

- 根因如上；判定依据：
  - `(this.plugin as any).deconstructionWorkerManager` 全仓仅此一处引用；
  - `SchedulerSegmentIntegration` 构造需要真实 `DeconstructionWorkerManager`，无法从插件取到；
  - 拆解结果零持久化，`viewResult()` 只提示“查看结果”而不展示任何内容。

### 2. 「批量拆解」命令保留、改指知识库

- `novel-writer-batch-deconstruct` 的 `CommandIds`、调色板注册、模式规则（LONG_ONLY）与注册快照**均未变**，三语义一致性测试零豁免继续通过。
- 执行器分支由构造模态改为 `openKnowledgeBase()`；调色板描述同步为“打开知识库：批量导入书籍并按维度拆解，结果持久化到拆解库”。

### 3. 能力没有损失

批量拆解一直有完整链路，且比原模态更可靠：

| 入口 | 行为 |
|---|---|
| `engine/batch-import-manager.ts:469` | 建书 → 存源文 → `scheduler.addTask(bookId, text, dimensions)`，幂等（重试不重复建书）、带进度与失败汇总 |
| `ui/views/knowledge-base-view.ts:2606 / 2942` | 拆解任务面板：进度、重试、删除、查看结果 |
| `ui/refill-modal.ts:639` | 单本补拆指定维度 |
| `ui/knowledge-monitor-modal.ts:474` | 监控面板重排任务 |

结果持久化在拆解库（`DeconstructionScheduler` 写 task 与 breakdown），可被指纹/风格库消费——这正是原模态缺的部分。

### 4. 基线同步（只降不升）

- any 108/49 → **106/48**（`--update-baseline --note`）；`scripts/optimization-advisor.mjs` 的 `FROZEN_ANY_PATHS` 清零（冻结桶机制保留，后续再冻结只需登记路径）。
- 内联样式 / JSDoc / 代码索引基线随文件删除重生成；JSDoc 导出覆盖 100%、`@example` 52/52、747 文件。
- bundle：main.js 4,871,801 → **4,864,382**（−7,419B），基线按“只降不升”收紧并写 note。
