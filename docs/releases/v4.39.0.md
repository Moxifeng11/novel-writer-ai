# v4.39.0 — 剩余 5 处裸读改写收口

发布日期：2026-11-05

## 为什么发这一版

v4.38.0 补齐 6 处核心读改写锁后，发布说明里明确列了 5 处仍未加锁的路径。本版逐项收口，全部按「最外层读 → 改 → 写整段进锁」处理，并补并发回归。

## 主要变化

### 1. 结算回滚路径

- `settleStep_finalizeRollback` 的 journal 回滚端口（`fs.read/write`、`readField/restoreField`）按文件路径加锁；回滚清理 `createdFiles` 的删除也加锁。
- `restoreSnapshots` 的 frontmatter 恢复加锁。
- 效果：结算失败回滚与协同保存/其它结算并发时，不会在「读旧值 → 写回」之间被第三方写入打断。

### 2. 伏笔库新建竞态

- `settleStep_createForeshadows`：文件是否存在从锁外移到锁内判断；锁内重读后再决定「追加到未回收伏笔 / 写基础模板」。
- 旧行为：两个并发结算都读到「库不存在」，后写者用基础模板覆盖前写者刚建好的条目。

### 3. 新增伏笔行号

- `addForeshadow`：存在性判断与 `getNextRowNum` 全部移入锁内，基于最新内容计算行号。
- 旧行为：并发新增可能重号；库不存在被并发创建时也可能整篇覆盖。

### 4. 伏笔追踪器

- 新增 `updateTracker(projectPath, mutate)`：锁内 `loadTracker → mutate → 写回`，供「读改写」场景使用。
- `saveTracker` 的整份覆盖写加锁（避免与 updateTracker 交错）；文档注明 saveTracker 仅用于整份快照覆盖。
- 回归：两个并发 `updateTracker` 的条目都保留。

### 5. 信息债看板

- `delete + write` 两步放进同一把锁，并发刷新不再出现「已删除但未写入」的空窗。

## 影响与迁移

- 破坏性变更：无（`saveTracker` 签名不变，新增 `updateTracker` 为增量 API）。
- 配置/数据迁移：无。
- 回滚建议：回滚到 v4.38.0 后上述并发窗口回归；已写入数据不受影响。

## 未完成（明确记录）

- `settleLight` 的正文 frontmatter 写入（`processFrontmatter`）仍未加锁，属正文文件写入，后续与 BodyWriter 的写锁策略统一处理。
- 信息债看板为派生产物，锁只保证 delete+write 原子性，不保证「此刻内容一定最新」。
- 伏笔追踪器的内存态 `this.tracker` 仍可能被多个项目复用（管理器单例），跨项目并发需调用方按项目重建实例或使用 updateTracker。
